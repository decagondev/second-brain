# sb-selfhost(7)

## NAME

sb-selfhost — a self-hosted cell on one machine, in containers

## SYNOPSIS

```text
make images                 # build one image per service
make selfhost               # the demo: an example tenant's cell on this machine's Docker
sudo tools/selfhost/install.sh [--install-docker] [--check] CONFIG   # an install on a Linux VM or server
sudo tools/selfhost/install.sh --doctor   # check the running box and say how to fix each problem
sudo tools/selfhost/install.sh --support  # a support bundle with no content and no secret in it
sudo tools/selfhost/install.sh --recovery-kit [--new-key] [--custodian N=NAME]…  # the recovery key, into 5 shares
sudo tools/selfhost/install.sh --retire [CONFIG] --yes-destroy   # destroy the box for good, with a signed statement
make selfhost-bundle        # an offline install bundle: every image and the install files
make selfhost-update        # one upgrade: admit the channel's release, start it by digest
tools/selfhost/update.sh --bundle FILE | --rollback | --resume   # offline upgrade, one step back, lift the hold
tools/selfhost/restore.sh [--dump FILE|s3:NAME [--key FILE]] | --drill  # restore the database, or prove a dump restores
tools/selfhost/restore.sh --from-kit KIT.sealed SHARE SHARE SHARE  # a new machine: the keys back from the kit
make selfhost-smoke         # check the running cell from outside
make selfhost-stop          # stop it; its data stays in Docker volumes
make selfhost-clean         # stop it and delete its volumes
```

## DESCRIPTION

A self-hosted cell is the whole cell on one machine: a VM or an on-prem server that holds a company's data on its own hardware, or a laptop for demos and testing. It runs the same images and the same sb-cell(5) configuration as a cell on GCP, laid out the way GCP lays one out (ADR-0022): one container per service, each with only what it needs.

**Images** (SB-1601). `make images` builds `sb-api`, `sb-ingest`, `sb-jobs` and `sb-updater` as static Go binaries (`CGO_ENABLED=0`, `-trimpath`, no build id) and puts each in its own image on the distroless static base, pinned by digest, running as the non-root user, with no shell. The `api` image also carries the built web UI (`/sb/web`). Each image's id is written to `build/images/digests.txt`, and `tools/release/bundle --image NAME=sha256:…` records it in the release bundle as `image/NAME`, which is what the updater deploys by (sb-release(7)). Each binary has its own SBOM, `build/images/NAME.spdx.json`. `DOCKER` names the Docker command (on Windows with Docker Desktop, its `docker.exe`).

**The layout** (SB-1602), `deploy/selfhost/compose.yaml`:

| Container | Like on GCP | Networks | Holds |
|---|---|---|---|
| `proxy` (Caddy) | the HTTPS load balancer | `edge`, `egress` | the only published ports (HTTPS, and HTTP for ACME's challenge); the install's TLS. The cell's own services reach the cell's public name through it |
| `api` | the `api` Cloud Run service | `edge`, `data`, `egress` | its own vault: sign-in, SCIM, the control plane, the model, connector credentials (for live checks), the anchor and attestation keys |
| `ingest` | the `ingest` Cloud Run service | `data`, `egress` | its own vault: connector credentials only |
| `jobs` | the `jobs` Cloud Run job | `data`, `egress` | its own vault: connector credentials, the anchor key and the write-once store's key pair |
| `updater` (run on a timer) | the `updater` Cloud Run job | `data`, `egress` | its own vault (empty unless the release store needs a pull token) and the release store, read-only |
| `worm` (versitygw) | the WORM Cloud Storage bucket | `data` only | every anchor and the backup's write-once copy, under compliance-mode object lock for seven years |
| `postgres` (pgvector) | Cloud SQL, private IP | `data` only, which has no route out | the database password; every record, the index and the audit log |
| `idp` (profile `bundled`) | the company's IdP | `edge` | sb-idp(1): its users' password hashes and its signing key, in its own volume; behind the proxy at `/idp` |
| `devidp` (profile `dev`) | none | `egress` | the development IdP, no passwords, on loopback only |

`data` is an internal network: Postgres can't reach the internet and nothing outside reaches Postgres. Each service's secrets are a vault of its own in a volume of its own, owned by the service's user and readable by nobody else (the vault refuses a secret others can read), so `ingest` never holds the sign-in secret, as on GCP each service account reaches only its own secrets. The shared `state` volume holds what sb-cell(5) keeps in files (job finishes, cursors, the usage ledger, kill switches) and the applied manifest. The database's DSN is in the vault too (`database: "vault://tenants/TENANT/database"` in sb-cell(5)), so the configuration file holds no secret.

**Write-once storage** (SB-1603). LAW-11 needs anchors and a backup copy that nobody, the cell included, can overwrite or delete for seven years. On GCP that is a bucket with a locked retention policy; on the box it is an S3 store with **compliance-mode object lock**, here versitygw on its own volume, reachable only on the `data` network. The cell talks to it with the standard S3 API, signed with Signature Version 4 in the standard library (`internal/adapters/backup/s3`), with the key pair at `vault://tenants/TENANT/worm` (sb-cell(5), `worm`). Before every write it reads the bucket's lock configuration and refuses a bucket without object lock, in governance mode (which an administrator can bypass) or with less than seven years. Every write carries `If-None-Match: *`, so a second write to a name is refused, and its own retain-until date in compliance mode. At install the one-shot `wormsetup` container makes the bucket, locks it, and proves the store enforces the lock: it writes a probe object and tries to delete it, version and all; a store that lets the delete through is refused, whatever its configuration claims. The probe stays, locked, as the proof. To keep a copy **off the box**, point `worm.endpoint` at an S3 store on another machine or site with compliance-mode lock, set `worm.offsite: true`, and list `{"worm": true}` in `backups`, so the backup's write-once copy is also its off-site one (sb-audit(7), Backups).

**Upgrades** (SB-1604). An install that writes a setting the running release doesn't know yet (an install bundle newer than the admitted release) finds the services refusing the configuration; it then starts the install's own images, as a first install does, keeps what ran for one rollback, and the upgrade that follows pins the admitted release again.  The updater has to deploy by digest, but a container that holds the Docker socket holds the whole machine, so no container does. The work is split. The `updater` container, run once per check, pulls the channel's release, admits it with the four checks of sb-release(7), attests each image digest, and records what each service should run under `state/deploy/services/`; that is all it can do. Then the host step, `tools/selfhost/update.sh`, run by `make selfhost-update` or by the `sb-selfhost-update.timer` systemd unit hourly (`deploy/selfhost/systemd/`), reads the record and refuses, before changing anything, a reference that isn't pinned by digest, an image the cell didn't attest, or an image this machine doesn't hold (a release whose images live in a registry is pulled by digest, which Docker checks against the content). It writes the digests, and nothing else, to `build/selfhost/compose.env` (`SB_*_IMAGE`), brings the services up on them, checks that each container runs exactly its digest, and records that under `state/deploy/running/`. The verifier's attestation reads `running/`, so it reports what the containers really run (sb-release(7), Attestation). A release the updater doesn't admit, unsigned, ungated or signed by another key, stops the host step at the first step: nothing changes, the unit fails, and the updater raises a Sev-1 `release_unsigned` alert. `make selfhost` publishes a **demo release** of this machine's own images, signed with a key made for this machine (`build/selfhost/release-key`, by `tools/selfhost/devrelease`) that only the demo configuration trusts; a real install trusts the factory's release identity instead (SB-1605).

**Install** (SB-1605). One script sets up every self-hosted cell, `tools/selfhost/selfhost.sh`; with no configuration it is the demo, and with `SB_CONFIG=FILE` it is an install, from a file of settings (`deploy/selfhost/install.env.example`):

| Setting | Meaning |
|---|---|
| `SB_TENANT`, `SB_MANIFEST`, `SB_POLICY` | the tenant, its manifest (sb-tenant(5)), and its own policy, optional |
| `SB_HOST`, `SB_PORT`, `SB_HTTP_PORT`, `SB_BIND` | where people reach the cell: on a VM its DNS name, 443, 80 and `0.0.0.0` |
| `SB_TLS` | `acme` (a public name; Caddy gets and renews the certificate), `files` (`SB_TLS_CERT`, `SB_TLS_KEY`, and `SB_TLS_CA` for a company CA) or `internal` (Caddy's own CA, for a lab) |
| `SB_IDP` | `company` (`SB_OIDC_ISSUER`, `SB_OIDC_CLIENT_ID`, `SB_OIDC_SECRET_FILE`), `bundled` (sb-idp(1)), or `dev`, which is refused unless `SB_BIND` is loopback |
| `SB_SHARE` | a directory for `docs: folder` (sb-connector(3)), mounted read-only into the cell; with the manifest's `notes: true`, its `notes/` folder alone is mounted writable into `api`, for stewards' notes (SB-1705) |
| `SB_OFFSITE` | the backup's off-box copy: a directory on another machine, mounted here |
| `SB_OFFSITE=s3://BUCKET/PREFIX` | or the company's S3 bucket instead (SB-2303), with its key pair in the file `SB_OFFSITE_KEY_FILE` names: `{"access_key", "secret_key"}`, and `"endpoint"` and `"region"` for a store other than AWS (default `https://s3.REGION.amazonaws.com`, `us-east-1`) |
| `SB_RELEASE_STORE`, `SB_RELEASE_TRUSTED`, `SB_RELEASE_PULL_TOKEN_FILE`, `SB_RELEASE_REGISTRY` | where releases come from (the factory's `https://` store, or a directory releases are copied into on an air-gapped site), the one identity that signs them, and where their images live |
| `SB_HTTPS_PROXY`, `SB_HTTPS_PROXY_FILE`, `SB_NO_PROXY` | the company's outbound proxy, optional (Outbound proxy, below) |
| `SB_EMAIL_SERVER`, `SB_EMAIL_FROM`, `SB_EMAIL_LOGIN_FILE` | notifications by email on a box without a chat bot, optional (Checking the settings, below; SB-2601) |
| `SB_DATABASE`, `SB_DATABASE_DSN_FILE`, `SB_DATABASE_CA` | `bundled` (the default) or `external`, the company's Postgres on another machine (A database on another machine, below) |

`sudo tools/selfhost/install.sh CONFIG` does the rest on a Linux VM or server: it checks the machine (Docker Engine and the compose plugin, installed from the distribution with `--install-docker`; systemd; an off-box directory that isn't on the root disk), loads the images of an **install bundle** (`make selfhost-bundle`: every image the layout runs and the files the install reads, for a machine with no Go, no Node and no internet) or builds them where Go is present, runs `selfhost.sh` with the configuration, applies the first release, and installs and starts the systemd units: `sb-selfhost.service` (the layout at boot, on the admitted digests), `sb-selfhost-update.timer` (hourly upgrades) and `sb-selfhost-dbdump.timer` (the nightly database dump). `--check` checks the machine and the configuration and changes nothing.

**Doctor and the box's health** (SB-1801, SB-1802). `install.sh --doctor` checks the running box: every service of the layout up (`proxy`, `api`, `ingest`, `jobs`, `worm`, `postgres`), both timers enabled with their last run successful, disk use of the install directory and of Docker's data root, the TLS certificate's expiry (`SB_TLS=files`; Caddy renews its own), `SB_OFFSITE` mounted from another machine and writable by uid 65532, the newest database dump and off-box copy, `/readyz` through the proxy, and whether the install directory, which holds the keys, is on an encrypted (LUKS) disk. `tools/selfhost/facts.sh` gathers the facts as one JSON document, reading state and never a secret, and `sb selfhost doctor` judges them (`internal/core/box`): each line is `pass`, `warn` or `fail`, with the command that fixes it, or `unknown` for a fact it couldn't gather, which is never shown as a pass. A disk warns at 80% and fails at 90%, a certificate at 21 and 7 days, a dump or off-box copy at 26 and 50 hours; a plain disk is a warning, never a refusal. Every line that isn't a pass carries its **fix** (SB-2605): one command, or a section of `docs/runbooks/selfhost.md` to read (`docs/runbooks/selfhost.md#restore`), printed by the doctor under the line and shown in the console's Box section; a test fails on a line without one, and on a fix naming a section the runbook doesn't have. It exits 1 if any line fails or is unknown and 0 otherwise (sb(1)), so a script can branch on it; `--json` gives the lines as JSON. The bundle carries `bin/sb`, so the box needs no Go (`tools/selfhost/sb.sh`). The hourly host step (`update.sh`) gathers the same facts first, before the updater runs, and leaves them in `state/host/facts.json`, where `GET /v1/admin/health` judges them with the same code for the console's **Box** section (sb-admin(3)); facts older than two hours are `unknown`. A failing check raises one Sev-2 `box_check` alert a day (sb-observability(7)).

**Restore and the drill** (SB-1803). `tools/selfhost/restore.sh` restores the database from a nightly dump in one command: the newest on the box, or `--dump FILE`. `dbdump.sh` writes a record beside each dump (`NAME.dump.json`: the tenant and the first 16 hex digits of the SHA-256 of the cell's audit anchor seed, never the seed), and a dump from another tenant or made under other keys is refused before anything stops, because its audit chain would verify under neither set of keys; to restore onto a new machine, put the old `build/selfhost` back first, or rebuild it from the recovery kit (below). Then it stops `api`, `ingest` and `jobs`, runs `pg_restore --clean`, starts them, waits for `/readyz`, and runs `sb audit verify` against the cell; a chain that doesn't verify fails the restore with the advice to check it before people come back. The index needs nothing: it rebuilds from the sources if it is older than the last sync (LAW-13). `restore.sh --drill` proves a dump restores without touching the cell: it restores the newest dump into a scratch database in a throwaway container with no network, checks that every table of the live database is in it, removes the container, and records the result in `build/selfhost/drill.json`; the live database is only read. `sb-selfhost-drill.timer` runs it monthly; the doctor and the console's Box section show the last drill, a warning after 35 days and a failure after 62 or when it failed.

**Offline upgrades** (SB-1804). An air-gapped box upgrades from a file. `update.sh --bundle FILE` takes an install bundle made with `SB_BUNDLE_RELEASES=DIR make selfhost-bundle`, which carries the release store's directory (`releases/`: the release, its signatures, its gate record and the channel) beside the images. It unpacks it into `build/selfhost/staging` (mode 0700, owned by root, removed afterwards) and, before anything reaches Docker, the box's **installed** `sb`, never the bundle's, runs `sb selfhost verify-bundle DIR --trusted KEY` (or `--cosign-identity ID`), the key or identity in the cell's own configuration: it admits the channel's release exactly as the updater does (sb-release(7), What a cell admits), and for each image the release names (`image/NAME`) finds the archive that is exactly that image (`release.VerifyImageTar`): every blob in the archive must hash to its name, `index.json` must name that one image and nothing else, everything the image reaches must be present, and there may be nothing else in the archive (no links, no paths outside the layout). It prints the archives to load and nothing if any check fails, and the upgrade then changes nothing and loads nothing. Only the verified archives are loaded; the release is copied into the cell's release store and the upgrade runs as above, so the updater admits it again. A bundle's third-party images (Caddy, Postgres, versitygw) change only with a new install, which pins them in `compose.yaml`.

**Rollback** (SB-1805). Each upgrade that changes a digest first keeps what ran before it in `build/selfhost/previous.env`: each service's image id, its attested reference and its release. `update.sh --rollback` starts exactly those, after checking that the cell attested each reference and the machine still holds each image, records them as running, and **holds** upgrades (`build/selfhost/held`), so the hourly timer doesn't move the box forward again; it then forgets the record, so a second rollback is refused: one step back, never two (LAW-08). `update.sh --resume` lifts the hold and the next run upgrades to the channel's release. The doctor and the console show a held box as a warning.

**Outbound proxy** (SB-1806). Most company networks reach the internet only through a proxy. `SB_HTTPS_PROXY=http://HOST:PORT` gives it to `api`, `ingest`, `jobs` and the updater, the four services with a route out, as `HTTPS_PROXY`; `postgres`, the `model` profile and the write-once store are on the `data` network alone and stay without one. A URL that carries credentials is refused there, because `install.env` and `compose.env` aren't secret: put the whole URL, credentials and all, in a root-only file named by `SB_HTTPS_PROXY_FILE`. The install copies it into each of the four services' own vaults (`https-proxy`) and gives them only its path, `SB_HTTPS_PROXY_FILE`, so the URL is never in a container's environment, where `docker inspect` would show it; each service reads it before it makes any HTTP client (sb-cell(5), Environment). Setting both is refused. The cell's own names never go through the proxy (its public name, for its sign-in, and the layout's services); `SB_NO_PROXY` adds the company's own hosts, such as an internal IdP or the share's server, in the usual comma-separated form. `sb selfhost check-proxy URL` (or `--file FILE`) checks a setting and prints the proxy's scheme and host only; a refusal never repeats the password. `install.sh --check` reports the setting.

**A database on another machine** (SB-1807). Some sites run Postgres on its own server, with its own backups, and want the cell on another VM. `SB_DATABASE=external` with `SB_DATABASE_DSN_FILE`, a root-only file holding the connection string (`postgres://…` or `key=value` pairs; Postgres 17 with the `vector` extension available), leaves the `postgres` container out of the layout (its compose profile `db` isn't started, and its volume stays), and `api`, `ingest` and `jobs` connect to that server instead, over the `egress` network, with the string in their vaults as before. The string must say `sslmode=verify-full`, so the cell checks the server's certificate and its name; anything less is refused, with the loopback addresses the only exception (`sb selfhost check-dsn FILE`, which prints the host only). A private CA for the server goes in `SB_DATABASE_CA`, which the install gives the services beside the proxy's (`/etc/sb/ca`). `dbdump.sh` and `restore.sh` work against it: they run the Postgres client in a throwaway container of the same image, with the string turned into a `pg_service.conf` (mode 0600, removed afterwards; `sb selfhost check-dsn FILE --service OUT`), so the password is in no process's arguments or environment. Moving between `bundled` and `external` takes effect on the next install: the services are started again on the new database. The doctor shows the marker `postgres-external` and doesn't look for a `postgres` container.

**Checking the settings** (SB-2601 to SB-2604). Each check names what is wrong and where it is fixed, and none prints a secret. **Email**: `SB_EMAIL_SERVER=HOST:PORT` and `SB_EMAIL_FROM` in `install.env` write sb-cell(5) `email`, for a box without a chat bot; a server that wants a sign-in reads it from `SB_EMAIL_LOGIN_FILE`, a root-only file (owner root, mode 0600 or 0400, otherwise refused) holding `{"username", "password"}`, which the install copies into the vaults of `api` and `jobs` (`email`) and nowhere else. `install.sh --check`, the install and `--doctor` run `sb selfhost check-email HOST:PORT [--ca FILE]`: the server answers, offers `STARTTLS` and shows a certificate the system's roots, and the company's CA in `SB_TLS_CA`, trust for `HOST`; it sends nothing and signs in to nothing. **A test**: `sb selfhost check-notify --to EMAIL --cell URL` (as an operator, with `SB_TOKEN`) sends that person the fixed test notification through the cell's real channel (sb-admin(3)) and says whether the channel took it; people use **Send me a test** in their notification settings. **The chat**: `sb selfhost check-chat --slack TOKENFILE` asks Slack (`auth.test`) for the bot's scopes and names each missing one of `commands`, `chat:write`, `im:write` and `users:read.email`, with where it is granted; `--mattermost URL --token-file FILE [--team ID]` asks Mattermost whether the account is a bot, a member of the team, and can see people's emails (*Show Email Address*). A token file holds the token, or the vault's JSON with `bot_token` (`build/selfhost/vault/api/vault/tenants/TENANT/mattermost`). `--api URL` points the Slack check at a test server. **The configuration**: `sb cell check-config FILE [--vault DIR]` runs the services' own check of a cell's configuration (sb-cell(5)) and names the line at fault, then confirms that each secret it needs (`oidc`, `scim`, `control-plane`, `audit/anchor-seed`, `attest-seed`, the database's, `mattermost` and `worm` when set, and `email` when there) is in the vault with owner-only permissions, by its file's mode and never its content. `update.sh` runs it on `build/selfhost/cell.json` against the api's vault before it restarts anything, so a typo, a missing secret or a secret others can read stops the upgrade with nothing changed. The install writes every vault file owner-only, and `update.sh` makes the files an older install wrote owner-only once.

**Support bundle** (SB-1808). When something breaks, `install.sh --support` writes one file to send to whoever helps, `build/selfhost/support-TIME.tar.gz` (mode 0600): the versions (the checkout or bundle, `sb`, Docker, compose, the kernel, and every running container's image id), the layout's settings (`compose.env` and `cell.json`, which hold names, paths and digests; their secrets are vault references), the last drill's record, the doctor's verdicts and the facts behind them, `ps`, and the last 1,000 log lines of each service. Settings that name files are kept as the names only; nothing under `/etc/second-brain` or `build/selfhost/vault` is copied in. Before the file is written, every file in it is scanned by `sb secrets scan` (sb-observability(7), Canaries and the secret scanner) against every value stored in the vaults and the box's own secret files (the database password, the write-once store's secret, the demo password, the release key), whole or in part (the secret field of a stored JSON object, one line of a key), and for the shapes of secrets (a private key, a URL with a password, a bearer token). Any finding names the file and line, never the value, and stops the bundle: nothing is written.

**Sealed off-box copies** (SB-1901). Whoever can read `SB_OFFSITE` could read the whole brain from a plain dump, so everything the box copies there is sealed first. The install makes a **recovery key** pair once (`sb backup keygen`): an X25519 key, its public half kept as `build/selfhost/recovery.pub`, its private half only until the recovery kit takes it off the box (below). Each file gets a fresh AES-256-GCM key, wrapped to the recovery key with an ephemeral X25519 key and HKDF-SHA256, and its content is encrypted in 64 KiB chunks, each authenticated and the last one marked (`internal/core/offsite`, standard library only), so a changed, dropped, reordered or truncated chunk fails to open and a file sealed to another key says so. The nightly dump goes off the box as `SB_OFFSITE/db/NAME.dump.sealed` (`sb backup seal`), with its plain record (`NAME.dump.json`: the tenant and the key fingerprint) beside it, and plain dumps copied there before sealing was on are removed; the nightly backup job seals every object of its off-box copy (`backups[].seal` in sb-cell(5); `NAME.sealed`), so its write-once copies stay readable on the box and in the write-once store and only the off-box one is sealed. Copies the job wrote before sealing was on stay as they are, because they are write-once. `sb backup open --key FILE` opens a sealed file and writes nothing if it doesn't open. Sealing is on by default; `SB_SEAL=off` turns it off and the doctor warns. The recovery kit's sealed archive goes off the box too (`SB_OFFSITE/kit/`).

**Off-box copies to S3** (SB-2303). A site with a bucket and no NAS sets `SB_OFFSITE=s3://BUCKET/PREFIX` and `SB_OFFSITE_KEY_FILE`, a root-only file with the key pair; the install copies the pair into the jobs service's vault (`vault://tenants/TENANT/offsite`) and nowhere else. The off-box copies then go to the bucket under `PREFIX/` through the same S3 adapter as the write-once store (`internal/adapters/backup/s3`, Signature Version 4, standard library), each written once (`If-None-Match: *`): the backup job's sealed copy (`backups[]` gains `{"s3": "s3://BUCKET/PREFIX", "offsite": true, "seal": "…"}`, sb-cell(5)), the nightly dump (`PREFIX/db/NAME.dump.sealed`), the recovery kit (`PREFIX/kit/`) and a retired box's export (`PREFIX/retired/`), through `sb backup push` and `sb backup pull`. **Nothing unsealed leaves the box**: an S3 copy needs sealing (`SB_SEAL=off` with `s3://` is refused, and so is a `backups[]` S3 copy without `seal`), and `sb backup push` refuses any file that isn't sealed, except a record of at most 4 KiB that is a JSON object (a dump's tenant and key fingerprint, a kit's custodians, never a share). The bucket needs no object lock, because the copies are sealed and written once; fourteen nights are kept by the bucket's own lifecycle rule (expire `PREFIX/db/` after 15 days), since the box never deletes there. `install.sh` checks the bucket before it changes anything, and `--doctor` lists it (`offsite` passes when the bucket answers with the key pair, fails when it refuses the key or isn't there, and is `unknown` when it couldn't be reached), with the newest dump there for the off-box copy's age. `restore.sh --dump s3:NAME.dump.sealed` pulls the sealed dump and its record from the bucket (`sb backup list` names them) and opens the dump with the recovery key, so a restore reads from the bucket as it does from a directory. On a new machine, fetch the kit first: `sb backup pull --from s3://BUCKET/PREFIX --keys KEYFILE --out DIR kit/kit_ID.sealed kit/kit_ID.json`. Any S3-compatible store works: the endpoint is in the key file, so a copy replicated to a second store restores from there by pointing the key file at it.

**The recovery kit** (SB-1902). The keys that make a restore possible live on the box, and a box that is lost or stolen takes them along. `install.sh --recovery-kit` takes them off it: it archives the box's keys (the vaults, the database and write-once store secrets, the recovery key pair and the demo's release key) and seals the archive with a fresh 32-byte kit key, which `sb recovery split` splits into **five shares, any three of which rebuild it** (Shamir's scheme over GF(256), `internal/core/shamir`); two reveal nothing about it. The sealed archive (`kit_ID.sealed`) and the kit's record (`kit_ID.json`: the kit, the tenant, the date, and with `--custodian N=NAME` who holds each share, never a share) stay in `build/selfhost/kit` and are copied to `SB_OFFSITE/kit/`. Then the recovery key's private half is deleted from the box (`shred -u`). Each share is one page to print (`kit_ID-share-N.txt`): its number, the tenant, the kit, 52 characters in groups of five, and a checksum, so a mistyped share is refused before it is used. Print each page, give it to its custodian, and delete the pages; the doctor warns while the private half or any page is still on the box, and fails when neither a kit nor a key exists. A lost share is survivable; to replace the kit, `--recovery-kit --new-key` starts a new recovery key (copies sealed before stay under the old kit). The bundled IdP's people aren't in the kit: after a recovery they are added again with `sb-idp user add`, and SCIM finds their directory ids in the restored database.

**Retiring a box** (SB-1907). When a company stops using a box, `install.sh --retire --yes-destroy` destroys it for good and leaves proof. Without `--yes-destroy` it lists what it would destroy and stops. With it, in this order: it runs the anchor job, takes the cell's audit export (`sb audit export --cell`) and checks it under the cell's own anchor key (`sb selfhost retire-statement --check`); if either fails, nothing is destroyed. A copy of the export goes to `SB_OFFSITE/retired/`, sealed to the recovery key like every off-box copy, because audit is kept for its seven years (sb-audit(7)). Then it stops and removes the systemd units, the containers and **every volume** (the database, the write-once store, the vaults, the sign-in, the TLS state), overwrites then deletes **every file under `build/selfhost`** with `shred -u` (the vaults and so every key, the database and write-once store secrets, the release key, local dumps), and checks that no volume and no file is left. Last it writes the statement, `build/retired/TENANT-TIME/statement.json`, with a copy in `SB_OFFSITE/retired/`: `{ "statement": "sb-retire/v1", "tenant", "host", "at", "destroyed": [...], "kept": [...], "last_anchor": { "seq", "hash", "signed_at", "sig", "key" }, "audit_rows", "key", "sig" }`. `last_anchor` is the cell's own signed anchor on its last audit row, so the statement says exactly where the chain ended. It is signed with an Ed25519 key made for this statement (`sb selfhost retire-statement`), whose private half is never written: the public key is printed, once, to be printed with the statement and kept by whoever needs the proof. `sb selfhost verify-retirement STATEMENT --key ed25519:KEY` checks it anywhere; any changed field, or another key, fails (`ECHAIN`). What stays: the sealed copies in `SB_OFFSITE` (dumps, the backup job's copies, the kit's sealed archive, the audit export), which open only with the recovery kit, any three of five shares; and, with `SB_DATABASE=external`, the company's own database, which the statement names for the company to drop. To destroy the off-box copies too, destroy the kit's shares: without three of them, the copies are noise.

**Recovering on a new machine.** With three shares and the off-box directory: put the bundle on the new machine, run `restore.sh --from-kit SB_OFFSITE/kit/kit_ID.sealed SHARE SHARE SHARE` (it refuses a machine that has keys already, checks each page's checksum and the rebuilt key against the kit's record, and writes the keys into `build/selfhost`, recording which shares were used in `build/selfhost/kit-used.jsonl`), then `install.sh CONFIG`, which keeps those keys, then `restore.sh --dump SB_OFFSITE/db/NAME.dump.sealed`, which opens the dump with the recovered recovery key, restores it and verifies the audit chain, and finally `install.sh --recovery-kit` again, so the recovery key leaves the new box too.

**Keys stay on the box.** Every secret and key is made on the machine by the install, once, and never leaves it: the database password, the OIDC client secret (or the company's, copied in), the SCIM token, the control plane's token, the anchor and attestation key seeds, the write-once store's key pair, and the bundled IdP's signing key. They sit in the per-service vaults under `build/selfhost/vault` (mode 0600) and in the volumes the install copies them into. Back that directory up with the machine's own encrypted backup or not at all; the release store and the factory never see any of it.

**Sign-in.** With `SB_IDP=company` the cell signs in with the company's OIDC IdP, which must send the cell's tenant in a `tenant` claim and the user's directory id in `sub` (sb-identity(7)) and provision users over SCIM. With `SB_IDP=bundled` it uses sb-idp(1), behind the proxy at `https://HOST/idp`: passwords as PBKDF2 hashes, failed sign-ins limited, and users added with `sb-idp user add`, which provisions them in the cell over SCIM so the directory and the IdP agree. The development IdP is refused by the install outright, and by `selfhost.sh` anywhere but loopback. When the proxy's certificate comes from Caddy's own CA or a company CA, `selfhost.sh` gives the services that CA's certificate (only the certificate) at `/etc/sb/ca`, so the cell can reach its own sign-in.

**Backups: three copies, one off the box.** The nightly `backup` job (sb-audit(7), Backups) writes the audit log and approvals to `state/backups` on the box, to the write-once store, and to `SB_OFFSITE`, so there are three copies on two kinds of media with one off the machine; it refuses to run with fewer. The nightly database dump (`tools/selfhost/dbdump.sh`, `pg_dump`) keeps fourteen nights of every other record on the box (`build/selfhost/db-dumps`) and off it (`SB_OFFSITE/db`, or `PREFIX/db/` in the bucket). The index can also be rebuilt from the sources (LAW-13).

**LAW-17 on one machine.** A self-hosted cell is in the company's custody from the start (`custody.tenant: true`). There is no IAM to enumerate, so the install writes the factory's access paths, which are at most the release store's read-only pull token, to `state/iam/TENANT.json`, and the cell keeps only that grant (`custody.retain`). The monthly `access` job checks the list, writes a **signed access statement** (`state/access/statement-DATE.json`: every path, the retained grants, anything unlisted) and records its SHA-256 in an `access` audit row, which the next hourly anchor signs into the write-once store, so the statement can't be changed afterwards without the chain showing it. An unlisted path fails the job with a Sev-1 `access_path` alert. Shell and Docker access to the machine itself is the company's own and is outside the cell; the runbook says to keep it to the company's administrators.

The runbook, [self-hosted install](../docs/runbooks/selfhost.md), walks through install, adding people, upgrades, backup and restore, and what to check after each.

**A model on the box** (SB-1710). With the compose profile `model`, the cell answers and embeds with models on its own machine, and no question leaves it. Two containers run llama.cpp's server (MIT licence) from one image pinned by digest: `model`, an instruct model for answers, and `model-embed`, an embedding model, each with its weights read-only from the `models` volume, as the service user on a read-only root, on the `data` network only, with no route out, no published port and no secret. The cell uses them as `model.provider: openaicompat` with `model.base: http://model:8080/v1` and `embed.provider: openaicompat` with `embed.base: http://model-embed:8080/v1` (sb-cell(5)); the model's price is 0, so the budget guard only counts. `make selfhost-model` (`tools/selfhost/model.sh`) tries it: given `SB_MODEL_GGUF` and `SB_EMBED_GGUF`, the weights files the operator has fetched, it records their SHA-256, resolves the image's digest, starts the profile, runs the eval gate's suites against that exact model through a loopback-only port that is removed afterwards, and switches the cell to it **only if the gate passes**; a model that fails the gate is never configured. It writes the model id and the weights' hashes to `build/selfhost/model.json` for the release bundle (`tools/release/bundle --model-weights`, sb-release(7)). `make selfhost-bundle` carries the weights files when `SB_MODEL_GGUF` and `SB_EMBED_GGUF` are set, so an air-gapped site never downloads them. **Hardware and latency:** a cell without the profile runs on 4 vCPU and 16 GB as before; with a 7 to 8 billion parameter model quantised to 4 bits it needs about 8 vCPU and 32 GB, or a small GPU. On CPU an answer takes tens of seconds: measured on Docker Desktop with 16 cores and 23 GB, Qwen2.5-7B-Instruct at Q4_K_M with nomic-embed-text-v1.5 answered in 7 to 32 seconds (median 15) over five asks, and the eval gate took 32 minutes (`make selfhost-smoke` prints the latency it measures). NFR-01's 6-second p95 is met only with a GPU; search (sb-ask(3)) stays the fast path. Changing to the profile's embedder rebuilds the index (sb-ingest(7)).

**The demo.** `make selfhost` with no configuration is a demo of the same layout on a laptop: the example tenant, the example share (`examples/share`, sb-connector(3)) to answer from, the bundled sign-in with one user, `ann@acme.example`, whose password it makes and leaves in `build/selfhost/demo-password`, Caddy's own CA, a stand-in off-box directory (`build/selfhost/.offsite`, a dot directory so Go's tools skip it, on the same disk, which a real install refuses to accept quietly), and a **demo release** of the machine's own images signed with a key made for the machine. The cell is at `https://cell.localhost:8443` (the browser warns about Caddy's certificate until it is trusted, `caddy trust` in the proxy container). Run `make selfhost-update` once to move the services onto the admitted digests. `SB_IDP=dev make selfhost` uses the development IdP instead, which signs in with no password and so refuses any address but loopback. **`make selfhost-smoke`** checks the demo from outside: the services' users and read-only roots; the UI over TLS; a wrong password refused and the right one signed in; answers that cite the share and never a file the asker can't read or one with no ACL file; the database network's missing route out; each vault's owner and mode; anchors in the write-once store and a refused delete; tonight's backup on the box, in the write-once store and off the box; the access statement; `sb tenant verify --cell` green; no Docker socket in any container; each service on its admitted digest; and a release signed with another key changing nothing. `make cell` (sb-runtime(7)) stays the flat, no-container way to run the same binaries for development.

## LAWS

[LAW-02](sb-laws.7.md#law-02): one machine, one tenant's cell. [LAW-06](sb-laws.7.md#law-06): the cell runs only a release it admitted, by digest, and an unadmitted one changes nothing. [LAW-11](sb-laws.7.md#law-11): anchors and the backup's write-once copy can't be overwritten or deleted for seven years. [LAW-07](sb-laws.7.md#law-07): each service reads only its own secrets, at call time, from files nobody else can read; a proxy's credentials stay in a file, and a support bundle carries no secret. [LAW-02](sb-laws.7.md#law-02) again: a database on another machine is reached only over TLS that checks its name. [LAW-16](sb-laws.7.md#law-16): the cell runs its applied manifest, kept in its own state. [LAW-17](sb-laws.7.md#law-17): the factory's only path to the cell is listed, checked monthly and stated in a signed statement. [LAW-18](sb-laws.7.md#law-18): every key is made on the box and held there, by the company, and the recovery kit's shares are its custodians when the box is gone: any three of five rebuild it, two don't. [LAW-11](sb-laws.7.md#law-11) again: what sits off the box opens only with the recovery key, and not at all once changed.
