# sb-ask(3)

## NAME

sb-ask — `POST /v1/ask`, `GET /v1/search`, `GET /v1/traces/{id}`, `POST /v1/feedback`, `/v1/saved`, `/v1/shares`, `/v1/questions`, `GET /v1/start`, `POST /v1/handover`, `GET /v1/handover/people`, `GET /v1/changes`, `POST /chat/mattermost`, `POST /chat/mattermost/actions`, `/v1/spaces/NAME/evals`, `POST /v1/access-requests`

## SYNOPSIS

```http
POST /v1/ask
{ "question": "What's our refund approval limit?" }
```

## DESCRIPTION

`POST /v1/ask` runs the `ask` agent for the signed-in user. The answer is built only from chunks that passed **live** authorisation for this user at this moment. Each claim either carries citations to `doc@version` or is marked `uncited`. How candidates are found and checked is in [sb-permissions(7)](sb-permissions.7.md#retrieval-and-the-live-check-exactly).

### Request

| Field | Type | Required | Meaning |
|---|---|---|---|
| `question` | string, ≤ 4,000 chars | yes | The user's question |
| `conversation` | string `cv_…` | no | Continue a conversation; earlier turns are re-authorised too |
| `sources` | list of kinds | no | Restrict to e.g. `["docs"]` |
| `language` | `en`, `de` or `fr` | no | (SB-3003) The language to write the answer's claims in. The web UI sends the person's chosen language; the chat apps send the manifest's `language` (sb-tenant(5)). Any other value is ignored, and without it the model writes as it does today |
| `documents` | list of `KIND:ID`, ≤ 5 | no | (SB-3004) Ask about these documents only: retrieval keeps only their chunks (Ask about a document, below). A version (`@N`) is ignored. More than 5, or one that isn't `KIND:ID`, is `EINVAL` |
| `length` | `short` | no | (SB-3303) `short` asks for at most 3 claims, the most important first, and the cell keeps at most 3. Each is still cited or marked `uncited`. Any other value is ignored, and without it the answer is as long as the model writes it |
| `verified` | boolean | no | (SB-3602) `true` answers only from **verified** documents: retrieval keeps only chunks of documents with a live **Reviewed, still right** mark at their current version (Documents to review, below), and published notes. It only narrows, after every check. If nothing verified is left, the answer is the `no_sources` one, as when nothing is found |
| `file` | `{ "name", "data" }` | no | (SB-3802) **Ask about a file**: one file, `data` its bytes in base64, at most 2 MB, of a type the folder connector reads (sb-connector(3): text, Markdown, PDF, Office, web pages, spreadsheets, transcripts), by `name`'s extension. Its text is read for this ask only, as ingest reads a document (hidden text stripped, instruction-like text flagged `injection_suspect`, secrets dropped, sb-ingest(7)), and its most relevant passages (at most 3, by the embedder) join the sources the live check allowed. The answer cites it as `file:NAME` with the title "Your file: NAME". Its text is kept nowhere: not in the index, and the trace keeps the answer as any trace does and of the file only that there was one (`"files": 1`), so a later **Show passage** on it says it is gone. It is no source in `verified`, `see_also` or `notice_sync`. A larger file, another type, or a file with no text is `EINVAL`. The web UI's **Attach a file** beside Ask sends it |
| `agent` | string | no | `ask` (default), or a department agent in its own template's space: `incident-summary`, `spec-digest`, `close-checklist`, `runbook-answer`, `policy-answer`, `clause-finder`, `account-brief`, `case-brief`, `brand-check`, `sop-steps`, `design-rationale`, `exec-brief` (sb-agents(7), Department agents) |
| `collection` | string `col_…` | no | (SB-4304) **Ask this collection**: ask about the documents of one collection the caller may read (Context for the work, below), at most 50, as `documents` does for five: retrieval keeps only their chunks, checked as the asker, so the answer cites nothing outside them. Its saved questions are not sources. An unknown collection, or one the caller can't read, is `EINVAL`; with `documents` too, `documents` wins |

In a cell with spaces, the space to ask in is the query parameter `?space=NAME` (sb-api(3), Spaces), never a body field: `POST /v1/ask?space=finance`. Without it the ask is company-wide. In a department, `&branch=true` (SB-3903) also asks in each of its teams the asker is a member of, every check running once per space as the asker in it (sb-spaces(7), The tree); it works the same on `GET /v1/search`, and a space with no teams, or none the asker is in, is the space alone.

### How the `ask` agent runs, exactly

1. **Validate.** `question` must be 1 to 4,000 characters after trimming, and `sources` may name only `docs`, `chat`, `tickets`, `crm`, `code`, `hris` or `accounting`. Unknown fields are ignored (sb-api(3), Versioning). Anything else is `EINVAL`.
   **Fair share** (SB-2305): each person may ask `asks_per_minute` times in any minute (sb-tenant(5), default 6), counted by the cell in its memory over a sliding minute. One more is `ERATE` (HTTP 429, with `Retry-After` and `retry_after`, the whole seconds until the oldest of the minute's asks is a minute old), with no model call, and is stored as a trace of agent `limited` with no question, so the weekly report counts it. The chat apps reply with the same wait. Search, saved questions, `sb tenant verify`'s sampled asks and everything else are not limited; a restart forgets the minute.
2. **Retrieve and check live** as in sb-permissions(7). With `sources`, candidates of other kinds are dropped before the live check. In a cell with spaces, every candidate first passes the space, label and barrier checks (sb-permissions(7), Spaces, labels and barriers) with the asker's read context; only the chunks they allow go into the live ACL batch, and the ACL still decides each of those. An ask in a space uses only what that space holds. A company-wide ask uses the union of the asker's spaces, plus `public` and `internal` content from spaces they aren't in; `confidential` and `restricted` content comes only from spaces they're a member of (SB-1006).
3. **No allowed context:** the model is **not** called. The answer is one uncited claim saying nothing the user can open answers this, with `notice` `no_access` if any candidate was refused, or `no_sources` if there were none.
4. **Compose:** the bundled `answer` prompt (with `language`, one more line: "Write each claim's text in German. Keep every label exactly as given.", or English or French), the allowed chunks as data blocks and the question go through the model gateway (sb-agents(7), MODEL GATEWAY). The composer decides citations (sb-citations(7)). Each stripped label is logged as `citation_spoof` with the trace id and the label, never the claim text.
5. **Notice:** `most_uncited` when more than half the claims are uncited; `notice_stale` and `notice_sync` as above, beside it.
6. **Trace:** every answer gets a new trace id `tr_…`, returned in the body and in `X-SB-Trace`, and stored with the answer and its decision list for 30 days.

**Conversations.** A request without `conversation` starts one, and the response carries its `cv_…` id in `conversation`. A later turn sends only the user's **earlier questions** to the model, never earlier answers or chunks: everything cited is retrieved and checked live again, so an earlier turn can't carry content the user has since lost access to. A `cv_…` id that isn't this user's is `EINVAL`, the same as one that doesn't exist. **Short conversations** (SB-2901): a later turn sends at most the **last 8** earlier questions, oldest first; any before them are left out of the prompt, and the response says how many in `earlier_dropped`. Nothing is removed from the stored conversation, and the trace keeps the turn's place in it. The web UI then says the earliest questions weren't used and offers **Start fresh**, which starts a new conversation.

**Answers in the asker's language** (SB-3003). `language` changes only the language the claims are written in. Retrieval, the live checks, the citations, the titles, sections and passages are the same as without it, and stay in the source's own language. An uncited claim is marked in every language (LAW-14). The language isn't stored with the question; the trace keeps the answer as written.

**The cited passage** (SB-3001). `GET /v1/traces/{id}/passage?cite=CITE&start=N` returns the text of one cite of that answer: `{ "cite": "docs:4f2a9c11@17", "text": "…", "cut": false }`. Only the person who asked (or an auditor, as for the trace) may call it, only for a cite that is in the trace's answer (`start` picks the span when the answer cites a document more than once; without it, the first), and every call checks the person's access to that document **again, now and as them** (sb-permissions(7)), so an old trace or a share can't show text they have lost access to. `text` is the cited chunk's text at that version, at most **600 characters**, cut after the last full sentence that fits (`cut` is then `true`). It is `EPERM` ("You can't open this source now.") when the live check denies or can't decide (LAW-01, LAW-03), and `200` with `"gone": true` and no `text` when the index no longer holds that version, which the UI shows as "This version is no longer indexed." A cite that isn't in the answer is `EINVAL`. Nothing is stored, and the text is never in a log (LAW-07). The web UI shows it as plain text in a block quote, never as markup (LAW-09).

**Ask about a document** (SB-3004). With `documents`, the candidates are only the chunks of those documents: those the search ranks, in its order, then the rest of each document's chunks in their order in it, so a document is found however the question is worded. They take every check as any candidate does, and the checks run first: the filter only ever narrows. A chosen document the asker can't open is refused like any other, so the answer is `no_access`; `refused` counts only the chosen documents. The three-chunk cap below doesn't apply, since every chunk is from a document the asker chose, but the usual budget does. Conversations, `language` and every notice work as without it.

**One document, three chunks** (SB-2902): of the chunks that pass every check and the one-copy rule (Copies, below), at most **3 of one document** go into what the model reads for an answer or a draft, its best-ranked ones, in rank order; the rest of the budget goes to other documents. Search results (`GET /v1/search`) are unchanged.

### Glossary, exactly (SB-2203)

In a space with a `glossary` (sb-space(5)), step 2 first **expands** the question: each term the question uses, as a whole word, adds its meaning to the text that is searched and embedded, so "PO" also finds documents that say "purchase order". A term with a capital letter matches only as written ("IT", never "it"); a term in lower case matches in any case. Only the space's own glossary is used, and only in an ask or search in that space: a company-wide ask, or another space, never expands one (LAW-19). An entry that reads like an instruction (the patterns of sb-ingest(7), Content is data) is never used. The terms used go to the model inside one data block, `<<data cite="glossary">>`, never as instructions (LAW-09), and the response lists them, `"terms": [{ "term": "PO", "means": "purchase order" }]`, which the web UI shows at the foot of the answer or results. The stewards' review list names the flagged entries, `"glossary_flagged": ["TERM"…]`, so they can fix them.

### Who to ask, exactly (SB-1702)

Every chunk carries its document's owner at the source (an email, SB-1203). The owner is looked up in the directory when the answer is built, and shown only if exactly one active user has that email; a deprovisioned, duplicated or unknown owner is left out, and a directory that can't answer leaves every owner out rather than failing the answer. Owners come only from the answer's cites, and a cite is only ever a chunk that passed the live check for this asker, so nobody learns who owns a document they can't open (LAW-01, LAW-12). Ownership at the source is the only signal: the cell builds no activity, chat or expertise profile of anyone. **Caretakers (SB-3405):** when a document's owner at the source is no active user, and a steward of the space named a caretaker for it, the caretaker is shown instead, with `"caretaker": true` on the owner, as long as they are one active user; a deprovisioned caretaker is shown as nobody (LAW-12). Whenever the source names an owner who is one active user, that owner is shown and the caretaker isn't.

### Search, exactly (SB-1701)

`GET /v1/search?q=TEXT[&sources=docs,chat][&space=NAME][&type=pdf,sheet,decision][&since=30d][&owner=EMAIL][&verified=true]` finds documents without the model. It runs steps 1 and 2 of the `ask` agent exactly (validation, retrieval, the space checks and the live ACL batch) and stops before the composer, so it makes **no model call** and uses no budget or tokens:

```json
{
  "trace": "tr_01JD3QC1…",
  "release": "rel_2027-03-02_9b1c4e",
  "results": [
    {
      "cite": "docs:4f2a9c11@17",
      "title": "Refund policy",
      "url": "https://…/refund-policy?version=17",
      "owner": { "email": "ann@acme-logistics.example", "title": "Support lead" },
      "age_days": 41,
      "snippet": "Refunds over £500 need a team lead's approval…",
      "flags": [],
      "spaces": ["support"],
      "label": "internal"
    }
  ],
  "refused": 1
}
```

| Rule | Detail |
|---|---|
| Results | Up to 20 documents, each once, in the order of their best-ranked allowed chunk. Only documents that passed every check for this asker now; a document whose check is denied, Unknown or late is never returned, only counted in `refused` (LAW-01, LAW-03) |
| `snippet` | The first 300 characters of the document's best allowed chunk: a quote of the source with its cite, never a claim (LAW-14). `flags` are that chunk's flags; in a chunk flagged `personal_data` each IBAN or card number is masked but its last four characters (sb-ingest(7), Personal data; SB-1904) |
| `age_days` | Whole days since the cell first indexed this version; omitted when the index doesn't know |
| `type` | Filters (SB-2404): only documents of these types, comma-separated, from the extension on the document's source id, else on its title: `pdf` (.pdf), `doc` (.docx, .doc, .odt, .rtf), `sheet` (.xlsx, .xls, .ods, .csv), `slides` (.pptx, .ppt, .odp), `web` (.html, .htm), `text` (.txt, .md), `transcript` (.vtt, .srt; SB-3701), and `other` for anything else, chat messages and tickets included. `decision` (SB-3702) is a passage, not a file type: a chunk under or holding a heading "Decision" or "Decisions" (any case, levels 1 to 3 as in sb-ingest(7), Sections), or the first chunk of a document whose front matter says `type: decision` (a first line `---`, then `type: decision` before the closing `---`). With `decision` the results are newest first, and in a space `q` may be left out to list the space's decisions, at most 50, each checked as any search is. `goal` (SB-4101) is the first chunk of a document whose front matter says `type: goal` (sb-ingest(7), Goals). An unknown type is `EINVAL` |
| `since` | Filters (SB-2404): only documents whose version the index first saw in the last `N` days (`Nd`, 1 to 365); one whose age the index doesn't know is left out. Both filters run **after** every check, on documents the asker may already open, so they only ever narrow: a filter never shows a document, and `refused` counts as without them |
| `owner` | As on a cite (Who to ask) |
| `verified=true` | (SB-3602) Only documents with a live **Reviewed, still right** mark at their current version, and notes, as for the ask's `verified`; it only narrows |
| `owner=EMAIL` | (SB-3306) Only documents whose owner, as shown (Who to ask), is that person: the filter runs **after** every check, so it only narrows, and an owner who isn't exactly one active directory user matches nothing. With `owner` the `q` may be left out: then the results are that owner's documents the asker can open now, newest version of each, by title, at most 20, read from the index and checked live like any search. Searches with `owner` are traced like any other, keeping the SHA-256 of `q` or of the empty string, never the email |
| `mine` | (SB-3106) `true` when the asker is the document's current owner at the source: its owner is one of the asker's own addresses in the directory now. Omitted otherwise |
| Errors | As for `POST /v1/ask`: `EINVAL` for an empty or over-long `q` or an unknown kind, `EKILLED` when the `ask` agent, the tenant or the space is killed, `EUNAVAIL` when the index or directory can't answer. Never `EBUDGET` |
| Trace | Every search gets a trace `tr_…` with its decision list, like an answer, with `agent` `search`. The trace keeps the SHA-256 of the query, never its text, and the policy kernel writes its decision rows to the audit log as for an ask |

The weekly report counts searches apart from answers.

### Saved and shared questions, exactly (SB-1703)

A person can keep a question and pass it on. Only the question's text is kept, never an answer: opening a saved or shared question asks it again, live, under the access of whoever opens it.

| Endpoint | Does |
|---|---|
| `POST /v1/saved` `{ "question": "…" }` | Saves a question (1 to 4,000 characters) in the space of the request. `200 { "id": "sq_…" }` |
| `GET /v1/saved` | `{ "items": [{ "id", "question", "space", "at", "watch" }] }`: the caller's own, newest first, at most 100 |
| `DELETE /v1/saved/{id}` | Removes one of the caller's own; anyone else's, or an unknown id, is `EPERM` |
| `PUT /v1/saved/{id}/watch` `{ "watch": true }` | Watches one of the caller's own (SB-2104), or stops with `false`; anyone else's is `EPERM`. `200 { "id", "watch" }` |
| `POST /v1/shares` `{ "question": "…" }` | Makes a share `sh_…` with an unguessable id and the link `/q/sh_…`, valid for 30 days. `200 { "id": "sh_…", "url": "/q/sh_…", "expires": "…" }` |
| `GET /v1/shares/{id}` | `{ "id", "question", "space", "expires" }` for any signed-in person of the same tenant. Another tenant's share, an unknown id or an expired one is `EPERM` (LAW-02) |

**Watching** (SB-2104) runs the question as a **search** (no model) as its owner, in its space, and keeps only the SHA-256 of the result set: each result's `cite`, which carries the version, sorted. Each week, with the digest (Notifications, below), the search runs again as the owner, now, and a different hash tells them the sources changed. A source they can no longer open drops out of the set, so it counts as a change, but nothing names it; no answer and no result is kept (LAW-07). A watched question whose owner is no longer active is skipped.

The link `/q/sh_…` opens the web UI on the shared question with an **Ask** button; asking it is an ordinary `POST /v1/ask` by the recipient, so they see only what their own access allows, never the sharer's answer (LAW-01). Creating a share writes an `access` audit row whose subject is the share id and whose `payload_sha256` is the SHA-256 of the question; the text itself never reaches a log or the audit log (LAW-07). Saved questions and shares are cell records kept under the tenant's retention (and a space's shorter one), held by legal holds like conversations, and erased with the person (`POST /v1/admin/subjects/erase`).

### What changed, exactly (SB-1708)

`GET /v1/changes?since=7d[&space=NAME]` lists documents with a version the index first saw in the window (`since` is `Nd`, 1 to 90 days), newest first, at most 50: `{ "since": "…", "items": [...] }`, each item a search result without the snippet. In a space, it lists what that space holds; company-wide, what the person's own spaces hold (in a cell without spaces, everything). Each document is checked as a search checks it, now, as the person, and one they can't open is left out; a version written by a rebuild is never listed (sb-ingest(7), Rebuild). The web UI shows "What changed this week" on the empty answer page, and the weekly report counts changed documents per space. The weekly digest (Notifications, below) sends each person this list, as them, when it is sent.

### Documents to review, exactly (SB-1709)

`GET /v1/spaces/NAME/review` is the stewards' list (the Cedar action `review_space`, as for access reviews): documents the space holds that answers cited at least 5 times in the last 30 days and whose version is older than the space's `review_after_days` (sb-space(5), default 365), and any document someone marked as a `wrong_citation` (POST /v1/feedback) in those 30 days. The counts come from the traces and feedback the cell already keeps. Each document is checked as a search checks it, now, as the steward: `{ "items": [{ …result, "cited": 7, "flagged": 1 }], "hidden": [{ "owner": "ann@…" }], "personal_data": 3 }`, where an item that is a note whose readers include people no longer members of the space carries `"wider": N`, their number (never who), and `"question": "qs_…"`, the note's question to republish it (SB-2004, listed first); where `personal_data` counts the documents the space holds with an IBAN or a card number in them (SB-1904), whether or not the steward can open them, and never says which; and where a document the steward can't open is only an entry in `hidden`, with its owner if there is one so they can ask the owner, never its title or cite.

**Reports and eval cases (SB-2204).** An item marked as a wrong citation carries `"reports": ["tr_…"]`, the traces of the answers reported (at most 10, newest first), so its stewards can turn one into an eval case: `POST /v1/spaces/NAME/evals`, `GET /v1/spaces/NAME/evals` and `DELETE /v1/spaces/NAME/evals/{id}` (sb-evals(7), Cases from wrong citations), with the same `review_space` decision as the list.

**Documents with no owner (SB-2201).** The list also holds documents the space holds whose owner at the source is no active user in the directory (someone who left, or was deprovisioned), each checked as the steward like the rest and carrying `"owner_gone": true`, with no `owner`: a deprovisioned owner is never shown as someone to ask, here or on any cite. A document with no owner at the source isn't listed for that alone. The directory is read when the list is asked for, so a deprovisioned owner's documents are on it at once, and in any case within the next sync. Those the steward can't open are entries in `hidden` with `"owner_gone": true` and nothing else. At most 50 are listed; a directory that can't answer is `EUNAVAIL`.

**Caretakers (SB-3405).** On a document with `owner_gone` that they can open, a steward names a caretaker: `PUT /v1/spaces/NAME/caretakers` `{ "doc": "KIND:ID", "email": "…" }`, where the email is an active member of the space now; anything else, a document the space doesn't hold or one whose owner isn't definitely gone, is `EINVAL`. It is one record per document, audited (`config`, `caretaker:NAME`, the hash of the email). The list's item then carries the caretaker as its `owner`, with `"caretaker": true`, and the owners' monthly note counts the document for the caretaker. `DELETE /v1/spaces/NAME/caretakers?doc=KIND:ID` removes it, audited the same way. The owner at the source wins again as soon as they are an active user.

**Terms the documents define (SB-3407).** The list carries `"terms": [{ "term": "PO", "meaning": "purchase order", "docs": 3 }]`, at most 20: definitions written as `purchase order (PO)` or `PO (purchase order)`, where the short form is 2 to 6 capital letters and the long form the same number of words with those initials, found in at least 2 of the space's documents that the steward can open now, and neither form already in the space's glossary. A chunk flagged `instruction_like` is never read, and a term whose text is flagged is skipped (sb-ingest(7)). It is a suggestion only: **Suggest** fills the Glossary form, which makes a proposal like any other (SB-3107); nothing changes until the proposal is applied (LAW-16).

**Teams (SB-3905).** A department's list carries `"teams": [{ "space", "to_review", "overdue", "open_questions", "found_nothing"?, "asks"?, "fewer_than_5"? }]`, one row per team under it (sb-spaces(7), The tree): how many documents on the team's own list the department's steward can open (never their titles, and never those they can't), its open and overdue questions, and this week's asks and those that found nothing, as on the team's own list. A team with fewer than 5 asks in the last 7 days shows `fewer_than_5` and no ask counts. Nothing but counts rolls up: never a title, a question or a person (LAW-24). The steward screen shows them under **Teams**.

**The right department (SB-4007).** A company-wide ask (no `space`, no `agent`) whose question uses, as a whole word, a glossary term of a space the asker is a member of, by their groups, and that runs a department agent (sb-agents(7)), gets `suggest`: `{ "space": "finance", "agent": "close-checklist", "terms": ["AP", "close"] }`. It is the one such space whose usable terms (sb-space(5), `glossary`, with its department's) the question uses most, then by name; a space whose agent is killed is passed over, and a term flagged as instruction-like never counts. It is a suggestion only: the answer is the same with or without it, and a space the asker isn't a member of is never named. The web UI shows "finance has an agent for this: close-checklist." with **Ask close-checklist in finance**, which asks the same question there, to that agent, as a new conversation.

**Who's who (SB-3906).** `GET /v1/spaces/NAME/people` is for any member of the space: `{ "space", "parent"?, "stewards": [{ "email", "title" }], "owners": [{ "email", "title", "cites", "caretaker"? }], "members": N }`. `stewards` are the people in its steward groups who are active users now. `owners` are the owners (or caretakers, SB-3405) of the space's ten most-cited documents this month, from its answers' traces, each named only for documents the asker can open now, through every check a search makes, and only when they are one active user (LAW-12); `cites` adds up how often their documents were cited. `members` is a count, never who. `parent` is the department, named only to a member of it too. A non-member gets `EPERM`. The web UI shows it on the space's Start tab.

**Usage of the space (SB-3506).** The list carries `"usage": { "space", "asks", "found_nothing_share", "helpful_share" }` for its own space over the last 7 days, the same row as the weekly report's (sb-observability(7), Usage by space): with fewer than 5 asks it is `{ "space", "fewer_than_5": true }` and no shares. Never another space's row.

**Copies (SB-2202).** Documents the space holds whose normalised text is the same (sb-ingest(7), Provenance) are listed once, as the newest copy the steward can open, with `"copies": [result…]`, the other copies they can open (title, cite and link; no snippet). Copies they can't open are entries in `hidden`. Answers, searches and drafts cite **one copy**: of documents with the same text that the asker can open, only the newest (the one the index saw last) is cited. Delete it, and the next answer cites the next newest.

**Reviewed, still right (SB-2501).** `POST /v1/spaces/NAME/review/marks` `{ "cite": "docs:…@17" }` marks a document on the list as reviewed at its **current version**: only a steward of the space, only for a document they can open now (otherwise `EPERM`, the same answer as for one that doesn't exist), and the cite's version must be the current one (`EINVAL` otherwise). The cell keeps `{ space, document, version, by, at }` and writes an audit row (`config`, state `reviewed`). A marked document leaves the list while its version is that one and the mark is younger than `review_after_days`; a new version, the mark's age, or a wrong-citation report **after** the mark puts it back. Reports before the mark no longer list it. The mark is the document's version, not the index's, so a rebuild neither clears nor renews it (LAW-13). **Review every N days (SB-3603):** the body may add `"days"`: 30, 90, 180 or 365; the mark then lasts that long instead of `review_after_days`, for the list, for Coming due, for `stale` on cites and for **Verified only**, and the mark keeps it as `days`. Any other value is `EINVAL`; without it nothing changes. **Unhelpful clears the mark (SB-3604):** a marked document is listed again, whatever the mark's age, once answers that cite it at the marked version have been rated **Not helpful** 3 times after the mark; the item carries `"unhelpful": N` and the screen says "rated unhelpful N times since its review". Ratings before the mark don't count, the same rule as wrong-citation reports, and the ratings are counted, never who gave them (LAW-07). Notes read wider than the space, documents with no owner and copies are listed whatever the mark, since a mark says the text is right, not that its readers or owner are. The answer is `{ "document": "docs:…", "version": 17 }`.

Every cite in an answer also carries `age_days` (whole days since the index first saw its version), and `stale: true` once that is past the `review_after_days` of a space that holds it (365 for a document no space holds). The web UI shows "N days old" on such a chip, in words, as part of its accessible name. A cite with a **Reviewed, still right** mark at its version (SB-2702) carries `reviewed`, and is `stale` only once `review_after_days` have passed since the mark, so a document a steward checked stops warning askers; its chip says "Reviewed 2026-11-20" instead. A new version is judged by its own age again. A document whose own `review-by` or `expires` date has come (sb-ingest(7), Review-by dates; SB-2705) is `stale` from that date, mark or not, and is on the review list once answers cite it at least 5 times, whatever a mark says.

**Reported outdated (SB-2703).** A document someone reported with `outdated_citation` in the last 30 days is on the list too, with `"outdated": N`, whatever its age. A **Reviewed, still right** mark clears the reports made before it, as it does wrong citations; a report after the mark puts it back.

**Retire from answers (SB-2801).** `POST /v1/spaces/NAME/retired` `{ "cite": "docs:…@17", "reason": "…", "replaced_by"?: "docs:…" }` takes a document out of the space's answers: only a steward of the space, only for a document the space holds and they can open now (otherwise `EPERM`, as for one that doesn't exist); `reason` is 1 to 200 characters; `replaced_by`, a document (`KIND:ID`, no version) the space holds and they can open, is optional. The cell keeps `{ space, document, reason, replaced_by, by, at }` and writes an audit row (`config`, state `retired`), and answers `{ "document": "docs:…", "reason": "…", "replaced_by": "docs:…", "at": "…" }`. From then on, answers, searches and drafts asked **in that space** skip every version of the document; a company-wide ask skips it only when every space that holds it retired it. The document stays at the source, in the index and in every other space, and a rebuild keeps it out, because the retirement is on the document's id, not the index (LAW-13). Like the cell's other records it is kept for `retention_days` (sb-tenant(5)); after that the document is back in answers unless a steward retires it again. A cite of the replacement carries `"replaces": "OLD TITLE"` when the asker can open the old document too, checked live. `GET /v1/spaces/NAME/retired` lists the space's retirements, each `{ document, reason, replaced_by, by, at }` with the title of a document the steward can open, and only a count of the others. **Bring back**, `POST /v1/spaces/NAME/retired/restore` `{ "document": "docs:…" }`, ends one, with an audit row (state `restored`), and answers `{ "document": "docs:…", "restored": true }`; one that isn't retired is `EPERM`.

**Same name, different text (SB-2802).** The list's `same_name` holds the documents the space holds whose titles are the same, ignoring case and spacing, and whose text differs, as groups, newest first: `[{ "title": "Leave policy", "items": [result…], "hidden": N }]`. Each group is checked as the steward like the rest: `items` are the ones they can open, `hidden` how many they can't. A group with fewer than two documents in all isn't listed; copies with the same text are listed once (Copies, below).

**Never cited (SB-2803).** `GET /v1/spaces/NAME/review?section=uncited` lists the documents the space holds that no answer cited in the last 180 days and that the index has held for more than 90, oldest first, at most 100: `{ "items": [result…], "hidden": [{ "owner": … }] }`, checked as the steward like the list. These are candidates to retire, nothing more: the section only reads the traces the cell keeps, and never shows a question. It also carries `"unused_terms": ["TERM"…]` (SB-2805): the space's usable glossary terms (sb-space(5)) that no answer asked in the space used in those 180 days, read from each trace's `terms`; a term used once isn't listed. Only the terms, never a question; a term is removed in the manifest, as any glossary change is.

**Eval cases to check (SB-2904).** The list carries `"evals_to_check": [{ "id": "ev_…", "question": "…", "check": "new_version" }]`, the space's eval cases whose expected document has a newer version or is gone (sb-evals(7), Cases that went stale). Omitted when none.

**Start here gone stale (SB-2907).** The list carries `"start_here": [{ "item": "docs:…", "result": {…}, "why": ["gone" | "stale" | "unreadable"], "members_without": N, "members": M }]`, the space's `start_here` items (sb-space(5)) that are **gone** from the index, **stale** by the rule in Answers, above, or that more than a quarter of the space's active members can't open now (**unreadable**: the live ACL for each member, where Unknown or late counts as can't, LAW-01), each with why. A folder item is judged by the documents under it: gone when there are none. `result` is the document as the steward can open it, checked as them; an item the steward can't open has no `result` and only counts, in `"start_here_hidden": N`. Members are checked in one ACL call each, at most 200 members; a bigger space counts the first 200. Omitted when every item is fine.

**Freshness (SB-2807). The list carries `"freshness": { "this_month": { "answers": N, "stale": N }, "last_month": { … } }`: of the answers asked in the space that cite anything, this calendar month and last (UTC), how many carried `notice_stale`, so rested mostly on stale cites (Answers, above). Counts from the traces only; the steward's screen shows each as a share.

**Notes whose sources moved (SB-2804).** A note (SB-1705) is a reply, which keeps the versions it cites. When one of them has a newer version in the index, or is gone from it, the note is on the list with `"sources_moved": N`, how many, until a steward republishes it or marks it **Reviewed, still right** after the change. The changed documents aren't named on the note's entry; the steward opens the note to see its cites, each checked as them.

**Questions that found nothing (SB-3101).** The list carries `"found_nothing": { "this_week": N, "last_week": N, "terms": ["PO", …], "counts": { "PO": N, … } }`: of the answers asked in the space, in the last 7 days and the 7 before, how many ended with `notice` `no_sources` or `most_uncited`, and the space's glossary terms those questions used (Glossary, exactly), most used first, at most 10. These are counts and the space's own terms, read from the traces, which keep no question text for this: no question text is shown, stored or sent (LAW-07). The stewards' line in the weekly digest (SB-2507) adds "N questions found nothing" when N > 0.

**Write the missing document (SB-3705).** Each of those terms on the review list has **Draft a note**: `POST /v1/spaces/NAME/drafts` `{ "term": "PO", "count": N }` (a term of 1 to 120 characters, a count of 1 to 10,000) puts a draft in the space's own queue, from the steward, with the term as its question and `draft: { "title": "PO", "comment": "Asked N times this week, found nothing" }`. The steward writes the text as the reply, and the note form opens with the term as the title; only **Publish as note** publishes it, through the note flow (SB-1705). Anyone but a steward gets `EPERM`; audited as `access`, state `drafted`.

**Question trends (SB-3704).** The stewards' line in the weekly digest also adds the space's most asked terms of the last 7 days: "asked most: cutoff 14, PO 9", the glossary terms of the space's answers (`terms`, counted as found-nothing counts them, but over every ask), each with at least 5 asks, most first, at most 5. A space with no term asked 5 times gets nothing added. Counts and the space's own terms only, never a question (LAW-07).

**Feedback for the stewards (SB-3104).** The list carries `"feedback": { "this_month": { "helpful": N, "not_helpful": N }, "last_month": { … }, "documents": [result…], "documents_hidden": N }`: the ratings given this calendar month and last (UTC) on answers asked in the space, and the documents cited most often in answers rated **Not helpful** this month, at most 10, most cited first, each checked as the steward like the rest of the list; `documents_hidden` counts the ones they can't open. Comments stay in the admins' queue (`GET /v1/admin/feedback`) and are never on this list.

**Conflicts (SB-3605).** The list carries `"conflicts": [{ "a": result, "b": result, "answers": N }], "conflicts_hidden": N`: the pairs of documents that claims marked **Sources disagree** (`disagree`, SB-3304) cited together in answers asked in the space this calendar month (UTC), with how many answers did, most first, at most 10. Each document is checked as the steward like the rest of the list: a pair is named only when they can open both, and `conflicts_hidden` counts the pairs they can't. Counts only: never who asked, the question or the claim. Omitted when there are none.

**Several at once (SB-3103).** `POST /v1/spaces/NAME/review/marks` and `POST /v1/spaces/NAME/retired` also take `"cites": ["docs:…@17", …]` (at most 50) instead of `cite`, with one `reason` and no `replaced_by` for a retirement. Each cite is checked, decided and audited on its own, exactly as when it is sent alone, and the response is `{ "items": [{ "cite": "…", "ok": true } | { "cite": "…", "error": { "code": "EPERM", "message": "…" } }] }`, in the order sent: one that fails doesn't stop the others. More than 50 is `EINVAL`. The review list has a checkbox on each document and **Mark reviewed** and **Retire** for the selected ones.

**Coming due (SB-3105).** `GET /v1/spaces/NAME/review?section=due` lists the documents the space holds that answers cited at least 5 times in the last 30 days, that aren't stale yet, and that turn stale in the next 14 days: `review_after_days` after their version was first seen, or after a **Reviewed, still right** mark at that version, or on their own review-by date (SB-2705), whichever is first. Soonest first, at most 100: `{ "items": [{ …result, "due_in_days": N }], "hidden": [{ "owner": … }] }`, checked as the steward like the list. **Reviewed, still right** works on them as on stale ones, and a mark moves the date on, except a document's own review-by date, which a mark doesn't lift. A document due in 10 days is listed; one due in 20 isn't.

**Owners mark their own (SB-3106).** `POST /v1/documents/reviewed` `{ "cite": "docs:…@17" }` lets a document's **current owner at the source** mark it **Reviewed, still right** at its current version: the document's owner must be one of the caller's own addresses in the directory now, and the caller must be able to open it now (the live check, LAW-01). Anyone else gets `EPERM`, the same answer as for a document that doesn't exist; someone deprovisioned can't sign in, and an address the directory no longer gives them isn't theirs (LAW-12). A version that isn't current is `EINVAL`. The mark is the stewards' own record, one for each space that holds the document, with the owner as `by`, so it shows on cites and takes the document off the review list exactly as a steward's does; each writes an audit row (`config`, state `reviewed`, reason `reviewed by its owner`) whose actor is the owner (LAW-11). The body may add `"days"` as a steward's mark does (SB-3603). The answer is `{ "document": "docs:…", "version": 17, "spaces": ["ops"] }`. In the web UI, a search result with `mine` has **Reviewed, still right** on the Documents tab.

### Start here and handover (SB-1706, SB-1707)

`GET /v1/start?space=NAME` is the space's reading list for a member (sb-spaces(7), Start here): `{ "items": [...], "hidden": 1 }`, each item a search result without the snippet. `POST /v1/handover` `{ "person": "usr_…" }` is the handover brief (sb-agents(7), Handover): `{ "trace", "person", "answer": { "claims": [...] }, "dropped", "hidden", "locations": { CITE: LOCATION } }`, every claim cited; `locations` gives where each briefed document lives, for documents the asker can open only (SB-2002). A refusal is `EPERM` with the policy's reason: only the person, their manager or a steward of a space they are in can have the brief, and an unknown person gets the same answer. `GET /v1/handover/people?q=TEXT` (SB-2106) finds the people the caller may brief: `{ "items": [{ "id", "name", "email", "title" }] }`, at most 20, sorted by name, whose user name or email contains `TEXT` (2 to 100 characters, case ignored). Candidates are the caller, the people whose directory manager is the caller, and the active members of spaces the caller stewards, and each one is kept only if the same policy decision as `POST /v1/handover` allows it now, so the list names no one the caller couldn't brief (LAW-01); a colleague with no relation isn't found whatever is typed. In the web UI the **Handover** tab finds a person by name or email with that list, or takes the person's user id, shows the brief grouped by location, and shows `hidden` as a count with the advice to have access moved to whoever takes the work over before the person leaves, since deprovisioning revokes their access (LAW-12).

### Questions to the stewards, exactly (SB-1704)

When nothing the asker can open answers (`notice` `no_sources`, `no_access` or `most_uncited`), they can send the question to the people who know: the stewards of the space they asked in (sb-space(5), `stewards`), or, for a company-wide ask, the manifest's `questions_to` group (sb-tenant(5)).

| Endpoint | Does |
|---|---|
| `POST /v1/questions` `{ "question": "…", "trace": "tr_…" }` | Sends the question to the stewards of the request's space (`?space=`), or to `questions_to` company-wide. `trace` must be the asker's own answer in that space with one of the three notices; anything else is `EINVAL`, and so is a space with no stewards or a cell with no `questions_to`. Only the question's text is sent: never the asker's name, the answer or its cites. `200 { "id": "qs_…", "to": "finance" }`. **Report this answer (SB-3606):** with `"report": true` and an optional `"note"` (at most 500 characters, one paragraph), `trace` is instead the asker's own answer in that space that they rated **Not helpful**, and the question goes to the same queue as a report of that answer, audited as `access`, state `reported` (the SHA-256 of the question and note, never their text). It is sent only by the asker's click, and it names them to the stewards, as the screen says before they send. A trace that isn't theirs, isn't rated Not helpful, or is a search is `EINVAL` |
| `POST /v1/questions` `{ "question": "…", "trace": "tr_…", "to": EMAIL }` | (SB-3706) **Ask the owner**: sends the question to one person instead of the stewards: an email among the answer's `people` (Who to ask), the owner or caretaker of a document the answer cites, who is one active user now. `trace` must be the asker's own answer in that space. It joins the person's own queue, `GET /v1/spaces/NAME/questions` with `me` as `NAME`, where they reply, claim and are notified as a steward is, and see only the question, never who asked. Their reply reaches the asker as a steward's does, cites checked as the asker; it can't be published as a note. Audited as `access`, state `asked`, reason "question to owner". A deprovisioned owner, someone the answer doesn't name, or more than one directory user with the email is `EINVAL` (LAW-12) |
| `DELETE /v1/spaces/NAME/questions/{id}` | (SB-3703) **Discard** a saved chat thread that has no reply: its text is dropped, the item leaves the queue, and an audit row (`access`, state `discarded`) says who. Anything but an open saved thread is `EINVAL`; anyone but a steward gets `EPERM` |
| `GET /v1/questions` | `{ "items": [...] }`: the caller's own questions, newest first, each `{ "id", "question", "space", "at", "state": "open"|"answered", "reply"? }` |
| `GET /v1/spaces/NAME/questions` | The queue of space `NAME`, or `company`, for its stewards: `{ "items": [{ "id", "question", "at", "state", "reply"?, "like"?, "overdue"?, "waited"?, "report"? }] }`, open ones first, never the asker, except on a report. `report` (SB-3606) is `{ "by", "note", "claims": ["…"], "documents": [result…], "hidden": N }`: who sent it, their note, the text of each claim of the reported answer whose every cite the steward can open now, and those documents by title, each checked live as the steward; `hidden` counts the claims and documents they can't open, never named. A report whose trace has expired shows only `by`, `note` and the question. `thread` (SB-3703) is a saved chat thread: `{ "by", "link", "text" }`, who saved it, a link to the thread in the chat app, and its messages as lines `EMAIL: text`. The steward publishes it by replying (the text is the reply box's start) and then **Publish as a note**, or discards it. `like` is another question of the same queue it looks like (SB-3402, Repeats, below). `overdue` is an open question 5 or more working days old (SB-3404). `waited` is on a question the company-wide answerers see because its own space left it open 10 working days: that number, with `from_space`. Anyone else is `EPERM` |
| `POST /v1/spaces/NAME/questions/{id}/reply` `{ "text": "…", "cites": ["docs:…@3"], "both"?: true }` | A steward's reply: text a person writes, 1 to 4,000 characters, and at most 10 cites the steward adds from their own search. Each cite must be one the steward can open now, checked live as a search is, or the reply is `EINVAL`. One reply a question; a second is `EINVAL`. With `"both": true` the same reply also goes to the question it looks like (`like`), when that one is still open: each its own reply, audited on its own, and each asker sees the cites checked as them (SB-3402) |
| `POST /v1/spaces/NAME/questions/{id}/note` `{ "title": "…", "readers"?: [EMAIL…], "keep_question"?: true, "confirm"?: N }` | With the manifest's `notes: true`, publishes the reply as a note (sb-spaces(7); SB-1705). Without `confirm` it only previews: `{ "path", "readers", "narrower" }`, the note's path, how many readers it will have (the space's active members, or the listed subset of them; never more) and how many of the reply's cites some of them can't open. The preview also carries `similar` (SB-3707): up to 3 documents the space holds whose text reads the same as the note's (the embedder's cosine of 0.85 or more, as Repeats uses), each a search result checked as the steward, so one they can't open is never named; it is a warning only. With `confirm` equal to that `narrower` count it publishes through the tool bus and returns `{ …, "action", "state", "receipt" }`; a different count is `EINVAL`. On a reply that is a note already it **republishes** it narrowed (SB-2004): the same text, under the title it was published with when `title` is empty, to the readers it has now who are still members of the space (or a listed subset of them), owned by the steward who first published it; it can only ever drop readers. The note is the title, the reply and its cites as sources; the question's text is in it only with `keep_question` (kept the same on a republish), and the asker is never named (SB-3401). Its front matter has `review_by:` 180 days from when it is published or republished, so it comes up in Documents to review and Coming due like any document (SB-3403; sb-ingest(7), Review-by dates). A question the company-wide answerers see because it waited (SB-3404) is published from its own space only |
| `POST /v1/spaces/NAME/questions/{id}/claim`, `DELETE /v1/spaces/NAME/questions/{id}/claim` | (SB-2502) "I'll answer this": the caller claims an open question for an hour, or lets their claim go. The queue then shows the question with `"claim": { "by": "ann@…", "mine": false, "until": "…" }` to the other stewards. A claim only warns: anyone can still reply, and a reply ends it. Claiming a question someone else claims answers with their claim, unchanged. A claim is shown only while it is live **and** its holder is an active member of the space's stewards now (LAW-21): someone removed from the group, or deprovisioned, loses every claim at once, and a cell that can't check shows none |

A space's templates are offered only in that space (LAW-19); the stewards of another space get `EPERM` |
| `GET /v1/spaces/NAME/suggested`, `PUT /v1/spaces/NAME/suggested` `{ "questions": ["…"] }` | (SB-3307) The space's suggested questions: `{ "questions": ["…"] }`, at most 8, each 1 to 120 characters of plain text, in the stewards' order. Only a steward of the space can set them, which replaces the list and writes an audit row (`config`, subject `suggested:NAME`, with the SHA-256 of the list, never its text). A reply is shown to the asker with its cites **checked live for the asker** each time they look, exactly as a search checks them: a cite they can't open now is dropped and counted (`reply.dropped`), never named, so a steward can't widen what the asker reads by quoting it (LAW-01). `reply.cites` has the same shape as a search result without the snippet. Who is a steward is decided by policy (`answer_questions` on the space, sb-policy(5)) with the caller's groups at that request, so a steward who leaves the stewards group stops seeing the queue at their next request (LAW-21). Sending writes an `access` audit row (`state` `asked`, the question's SHA-256) before the question is stored, and a reply one (`state` `answered`, the reply's SHA-256) before it is stored (LAW-04); neither row holds text (LAW-07). Questions are cell records under the tenant's retention, or the space's shorter one, so an unanswered question ages out with it; they are held by legal holds on their space and erased with the asker. The weekly report counts questions asked and answered per space, never their text.

**Verified answers (SB-3601).** A steward of the space pins a good reply as the space's answer to its question: `POST /v1/spaces/NAME/pins` `{ "question_id": "qs_…", "question": "…" }` takes an answered question of the space's queue whose reply has at least one cite, with the question as it should be shown to askers (1 to 300 characters; without it, the question as asked, which the steward should check names no one). The pin keeps the question, the reply's text and its cites, who pinned it and when: one record of at most 50 pins per space, each pin audited (`config`, subject `pin:NAME`, state `pinned`, the SHA-256 of its question and text, never the text). `GET /v1/spaces/NAME/pins` lists them for the space's stewards, each with `due: true` once older than `review_after_days`, when it is no longer shown; pinning the same question again renews it. `DELETE /v1/spaces/NAME/pins/ID` removes one, audited as `unpinned`. A 51st pin, a question without a cited reply, or another space's question is `EINVAL`; anyone but a steward gets `EPERM`. An ask in the space shows a matching pin as `pinned` (Response, above).

**Repeats (SB-3402).** When a question is sent, the cell embeds it with the embedder it already has and compares it with the newest 200 questions of the same queue from the last 90 days, open or answered. The closest one with a cosine of 0.85 or more is kept as the new question's `like`, and the older one shows the new one as its `like` while the new one is open. Only the stewards see it, as **Looks like qs_…** on the steward screen; the asker never sees another asker's question or that there is one. A cell without an embedder, or an embedder that fails, links nothing and the question is sent as before. **Answer both** is the reply with `"both": true`.

**Old questions (SB-3404).** Working days are Monday to Friday in the manifest's `digest` time zone (UTC without one), counted from the day after the question was sent. An open question is `overdue` from 5 working days: the steward screen marks it **Overdue**, and the steward's digest line counts it first. From 10 working days the notify job also shows it to the company-wide answerers (`questions_to`, sb-tenant(5)), as long as nobody holds a live claim on it (SB-2502; a claim waits until it lapses), it is in a space and not company-wide, and the cell has `questions_to`. It stays in its own space's queue too, with `waited` and `from_space` on the company-wide queue, shown as "finance hasn't answered this in 10 working days". The job writes one audit row per question (`access`, `rerouted`, by `sys_notify`), and tells the company-wide answerers "1 question waited 10 working days in its space" with a link to the company steward screen. Counts only; never the question or who asked.

**Up the tree (SB-3904).** In a team space (sb-spaces(7), The tree), the first step goes to the team's **department** instead: after 10 working days the department's stewards see it in their queue, with `waited` and `from_space` ("ap hasn't answered this in 10 working days"), and are told "1 question waited 10 working days in a team" with a link to the department's steward screen. After 10 more, if it is still open and unclaimed, it goes on to the company-wide answerers as above. It stays in every queue it reached; each step is one audit row (`rerouted`, its reason naming where it went) and the question records the queues it reached as `up`. A department's stewards answer it from their own queue, as they would one of theirs, and the asker gets the reply as from the team. A step whose queue has no stewards waits.

### Goals, updates and policies (SB-4101 to SB-4103)

**Goals.** A goal is a document whose front matter says `type: goal`, with `owner`, `quarter` (`YYYY-Qn`), `status` (`on_track`, `at_risk`, `off_track` or `done`) and, optionally, `parent_goal` (the title or source id of a goal in the space above; sb-ingest(7), Goals). `GET /v1/spaces/NAME/goals` lists the goals of the space and of the teams under it that the caller is a member of, each checked as the caller (LAW-01): `{ "space", "quarters": [{ "quarter", "goals": [{ "title", "ref", "owner", "status", "space", "parent"?, "children"? }] }], "hidden" }`, newest quarter first, a team's goal nested under the department goal it names. `hidden` counts goals the caller can't open, never which. A goal whose parent the caller can't open stands at the top.

**Status updates.** A space with `updates: true` (sb-space(5)) gets the `update` agent's draft every Monday as a thread its steward publishes as a note under `notes/NAME/updates/` (sb-agents(7), The update agent). `GET /v1/spaces/NAME/updates` lists the latest published update of the space itself and then of each team under it (SB-4106): `{ "space", "updates": [{ "space", "title", "ref", "at" }], "hidden" }`, each checked as the caller; a team without one isn't listed.

**Policies to read.** A steward marks a document in their space's branch as a policy: `POST /v1/spaces/NAME/policies` `{ "doc" }`, at most 50 a space, audited `policy_marked`. The steward must be able to open it. `GET /v1/spaces/NAME/policies` gives a member the policies of their space and the spaces above it that they can open, with `read: true` when they have read the current version. `POST /v1/spaces/NAME/policies/read` `{ "doc", "version" }` records a read of the current version only (an older version is `EINVAL`), audited `policy_read` with no text. A new version makes everyone unread again. `GET /v1/spaces/NAME/policies/status` gives a steward, per policy, `not_read` (the members of the branch who haven't read it, by email), `read` (a count) and `cant_open` (a count of members who can't open it, who are never asked to read it). Members get the `policy` notification (Notifications, above). Errors are `EPERM` for someone who isn't a member (or a steward, where it says so) and `EINVAL` for a document that isn't in the space's branch or that the steward can't open.

### Research, meeting prep and action items (SB-4201 to SB-4203)

These are the legwork agents (sb-agents(7), The legwork agents). Each runs on the `ask` path as the person, with every check a search makes, has no tools, and leaves its result for that person, or a draft for a steward. A result is **stored** and read later, so every cite in it is **checked again as the reader each time it is shown** (LAW-26): a cite the reader can no longer open, through every check a search makes, is removed, a claim left with no cite is removed too, and `dropped` counts them. Nothing is checked for anyone but the reader; a report is only its owner's.

**Research reports** (SB-4201). `POST /v1/research` `{ "question": "…", "documents"?: ["KIND:ID"…] }`, in the scope's space (`?space=NAME`, or company-wide), asks the `research` agent to break the question (1 to 300 characters) into **at most 10 sub-questions**. It sends the model the question only, never a document; each line it gives becomes a step, cut to 300 characters, and a plan with no usable line has the question itself as its one step. The answer is the **plan**, which runs nothing yet: `{ "id": "rs_…", "kind": "research", "question", "space", "steps": ["…"], "state": "planned", "at" }`, audited (`access`, `planned`, the SHA-256 of the question). `POST /v1/research/{id}/run` starts it: only its owner, only a plan whose state is `planned` (otherwise `EINVAL`), audited `queued`. The notify job (sb-runtime(7)) then runs at most 3 queued reports a run, oldest first, as their owner: each step is one ask, with the plan's space and `documents`, writing its own trace, and a step whose answer cites nothing adds no section. It stops, and keeps what it has, at the tenant's `research_usd` (sb-tenant(5), default $2, the model's price of the tokens the report's asks used) or when the owner's space or the tenant is out of budget (`EBUDGET`, sb-observability(7)); `stopped` then says `cap` or `budget`. An owner who is no longer active, or whose ask fails, ends it as `failed`, with `why` and no text. A finished report is `done`, and its owner gets one `research` notification (Notifications, below). `GET /v1/research` lists the caller's own reports and meeting briefs of the last **30 days**, newest first: `{ "items": [{ "id", "kind", "question", "space", "state", "steps": N, "at", "done_at"? }] }`. `GET /v1/research/{id}` is the whole report for its owner only (anyone else, and a report older than 30 days, gets `EPERM`, as for one that doesn't exist): `{ "id", "kind", "question", "space", "state", "why"?, "steps": [...], "at", "done_at"?, "cost_usd", "stopped"?, "summary": [claim…], "sections": [{ "question", "trace", "claims": [claim…] }], "dropped": N }`, where `summary` is the first claim of each section, and every claim is checked again as above. The web UI's **Legwork** tab shows the plan with **Run**, and the report (The web UI, below).

**Meeting prep** (SB-4202). `POST /v1/prepare` `{ "agenda": "…", "title"?: "…", "attendees"?: ["email"…] }` (an agenda of 1 to 4,000 characters; at most 50 attendees), or `{ "event": "ID" }` for an event in the caller's own calendar (Calendar, below), in the scope's space or company-wide. The agenda's items are its non-empty lines, with bullets and numbers stripped, at most **8**, each cut to 300 characters; the agenda is **data, not instructions** (LAW-09). Each item is asked once, by the `meeting-prep` agent, as the caller. The brief has a report's shape, with `"kind": "prep"`, the meeting's title (or "Meeting") as `question`, one section per item, `{ "question": ITEM, "trace", "claims", "decisions"?: [cite…], "questions"? }`, and `"attendees": [{ "email", "known": bool, "owns"?: [cite…] }]`: for each item its cited claims; the **decisions** (sb-ingest(7), Decisions) of the last 90 days in the space that the caller can open and whose titles share a word of 4 or more letters with the item, at most 3; and, only for a steward of the space, `questions`, how many of the space's open questions share such a word (a count, never a question). For each attendee, `known` is whether they are one active user in the directory now (LAW-12), and `owns` lists the documents the brief cites whose owner at the source is that person. Anyone not known is shown only as the address was written, with no `owns`. A brief is stored like a report (`kind: "prep"`, 30 days, checked again as the reader when opened with `GET /v1/research/{id}`), and listed with them.

**Calendar** (SB-4202). A cell with sb-cell(5) `calendar` reads each person's **own** calendar, read-only, as them (sb-connector(3), Calendars). `GET /v1/me/events` lists the caller's events of the next 7 days: `{ "events": [{ "id", "title", "start", "attendees": N, "agenda": bool }] }`; `agenda` says the event has a description to prepare from. A cell without `calendar` answers `EUNAVAIL`, and `event` is `EINVAL` there. **Prep before each meeting:** `PUT /v1/me/notifications` `{ "prep": true }` (and `false` to stop; shown as `"prep": true` in the settings) has the notify job prepare, as the person, each of their events that has a description and starts 25 to 35 minutes after the job's run, once per event, and send one `prep` notification; nothing is fetched for anyone who hasn't turned it on.

**Action items** (SB-4203). A new transcript's decisions draft (sb-agents(7), Scheduled and triggered agents) also lists the meeting's **action items**, read from the transcript as the steward it runs as, without the model: each line that starts `Action:`, `Action item:`, `TODO:` or `AI:` (any case), at most 20, each cut to 300 characters. Its **owner** is the `@name` or the one to three words before ` to `, ` will ` or ` should ` at its start, as said; its **due** date is a `by YYYY-MM-DD` or `due YYYY-MM-DD` in it. An owner matches a tenant user when one active user's email, before the `@`, or `userName`, is that name, ignoring case and spaces; otherwise it stays as said. The draft carries them as `actions: [{ "text", "owner", "email"?, "due"? }]`, seen only by the steward who sees its text. **Nothing is told to anyone until that steward confirms them**: `POST /v1/spaces/NAME/actions` `{ "draft": "qs_…", "items": [{ "text", "owner", "due"? }] }` (at most 20; the text 1 to 300 characters, `due` a date), from the steward the draft ran as, while the draft is open; anything else is `EPERM` or `EINVAL`. Each item becomes one record `{ "id": "ac_…", "space", "doc", "text", "owner", "user"?, "email"?, "due"?, "by", "at", "done_at"? }`, its owner matched again, audited (`access`, `action_confirmed`, the item's hash). Each matched owner is told once (`action`, Notifications, below); an unmatched one is told nothing. `GET /v1/me/actions` lists the caller's own items, open and those done in the last 30 days, with `"overdue": true` past their due date. `POST /v1/me/actions/{id}/done` marks one done: only its owner (`EPERM` otherwise), audited `action_done`. `GET /v1/spaces/NAME/actions` gives a member of the space its open items whose transcript they can open now, checked as them (LAW-01), and `hidden`, how many others. Nothing is sent to a tracker.

### Follow-ups (SB-4204 to SB-4207)

**Incident briefs** (SB-4204) and **customer themes** (SB-4205) are agent drafts in a steward queue (sb-agents(7), Scheduled and triggered agents; The legwork agents).

**Draft a fix** (SB-4206). `POST /v1/spaces/NAME/review/fix` `{ "doc": "KIND:ID" }`, from a steward of the space, for a document of the space they can open (otherwise `EPERM`, as for one that doesn't exist). The document's owner at the source must be one active user who is a member of the space (otherwise `EINVAL`). The `fix-draft` agent runs **as the owner**, so it uses only what they can open, and keeps only the changes that cite a document other than this one; with none, `EINVAL`. The suggestion is stored for the owner like a report (`kind: "fix"`, `"question": "Suggested edits: TITLE"`, one section of changes, 30 days, checked again as the reader when opened with `GET /v1/research/{id}`; LAW-26), audited (`access`, `fix_suggested`, the hash of the document's cite), and the owner gets one `fix` notification. The answer is `{ "id", "owner", "changes": N, "told": bool }`. Its `state` is `suggested` until the index holds a newer version of the document, then `applied`. **Nothing is written to the source**: the owner edits it there.

**Goal check-ins** (SB-4207). Each Monday a goal gets a check-in draft in its space's queue, run as its owner (sb-agents(7)). The owner replies with it and publishes it as a note, which is written under `notes/NAME/goals/` (sb-connector(3), Notes); nothing is published without them. `GET /v1/spaces/NAME/goals` marks a goal not `done` with `"silent": true` when no check-in for it has been published for 21 days, or, with none ever, 21 days after it was first seen; the space's home shows "No check-in for 3 weeks". Only the goals the caller can open are listed, so a department sees its teams' silent goals only as it sees their goals (LAW-24).

### Work that comes to you (SB-4301 to SB-4303)

**One inbox** (SB-4301). `GET /v1/me/inbox` is everything that waits on the caller, across every space, in three lists: `{ "needs_you": [item…], "failed": [item…], "done": [item…], "counts": { "needs_you": N, "failed": N, "done": N } }`. Each item is `{ "kind", "id", "space"?, "title", "at", "due"?, "overdue"?, "why"?, "link" }`, newest first, with overdue items first in **Needs you**. It is built **when it is asked for, as the caller** (LAW-26), from the calls each item's own tab makes, so it shows exactly what those show them now:

| `kind` | Needs you | Done (the last 30 days) |
|---|---|---|
| `draft` | An open agent draft (sb-agents(7)), a saved chat thread or a found-nothing draft in a steward queue the caller answers now (Questions to the stewards, above), not claimed by someone else | One the caller replied to |
| `question`, `request` | An open question or request in such a queue, or in the caller's own queue (Ask the owner), not claimed by someone else; a request past `due` is `overdue` | One the caller replied to |
| `policy` | A policy to read that applies in a space they are a member of and that they can open, not read at its current version (SB-4103) | |
| `approval` | An action waiting for the caller's approval group (sb-actions(3)), never across a barrier from its requester | |
| `action` | Their own open action item whose transcript they can open now, `overdue` past its date (SB-4203) | One they marked done |
| `fix` | Suggested edits to one of their documents, while `suggested`, whose document they can open now (SB-4206) | |
| `research` | A plan waiting for **Run** | A finished report or brief |
| `routine` | | A routine's answer (below) |
| `case` | A candidate eval case of an agent they answer for (sb-evals(7), Cases from feedback; SB-4401) | |

**Failed** holds their research reports and routine runs that `failed`, each with `why`. An item whose space they left, whose queue they no longer answer, or whose document they can no longer open is simply not there, never counted. `title` is a question as it was sent, a draft's or policy's title, an action item's text or a workflow's name; `link` is where it is acted on (`/?steward=NAME`, `/?space=NAME`, `/?action=ID`, `/?tab=legwork` or `/?tab=questions`). **The inbox only lists: every action happens on that page**, through its own call and checks. Its counts are the lengths of the lists, so they match the tabs; notifications still say only counts (Notifications, below).

**My routines** (SB-4302). `PUT /v1/saved/{id}/routine` `{ "every": "daily" }`, or `{ "every": "weekly", "day": "monday" }` (any day Monday to Friday), makes one of the caller's saved questions a **routine**; `{ "every": "off" }` stops it. At most **5** per person: a sixth is `EINVAL`, as is another person's question (`EPERM`). The saved question then carries `"routine": { "every", "day"?, "last"? }`. The notify job asks each routine due, at most 10 a run: a daily one on each working morning at 08:00, a weekly one on its day at 08:00, both in the `digest` time zone (sb-tenant(5)), the first time at the next of those after it was set. Each run is an ordinary ask **as the person, now**, in the saved question's space, with their memory (below), writing its own trace, so it cites only what they can open at that moment. Its answer is kept for them like a report (`kind: "routine"`, its question, one section, 30 days) with `changed`, how many of its sources are new or have a new version since the last run, and the claims that cite one of those **first**. It is listed by `GET /v1/research` and opened with `GET /v1/research/{id}`, where it is checked again as the reader (LAW-26), and the person gets one `routine` notification (below). A run when the person's space or the tenant is out of budget is **paused**: it is kept as `failed` with `why` "paused: the budget for this month is spent", nothing is sent, and the next due run tries again. A person who is no longer active is never asked for (LAW-12): their routines do nothing, and nothing is kept. Every run is audited (`access`, `routine`, the SHA-256 of the question). The Saved tab has **Routine: off, daily, weekly** on each saved question.

**Memory I control** (SB-4303). A person can tell the brain a few things about themselves, in their own words: their role, team, the format they like, their language, a default space. `GET /v1/me/memory` is `{ "on": bool, "lines": [{ "id", "text", "at" }] }`. `POST /v1/me/memory` `{ "text": "…" }` adds one line: plain text on one line, 1 to **200** characters, at most **20** lines (`EINVAL` otherwise). A line that repeats a document is refused (`EINVAL`, "That reads like a document, not something about you"): the cell searches for it as the person, and refuses it when one of the passages they can open holds it, or 8 words of it in a row, ignoring case, spaces and punctuation. When that search can't run, nothing is kept (LAW-03). `DELETE /v1/me/memory/{id}` removes one line, and `DELETE /v1/me/memory` all of them; each change is audited (`access`, `memory`, the SHA-256 of the line, never its text). Each of the person's **own** asks to the `ask` agent, their routines included, sends their lines to the model as a block marked as the asker's own words about themselves, never as a source, so nothing can cite it (LAW-14). Department and legwork agents, agent drafts and eval probes never carry it. **LAW-25**: a memory holds only what its person wrote, never text from a document, and it is sent with no one else's ask. The lines are in **Download my data** (`memory`), erased by **Forget my questions** at once, erased with the person, and never expired by retention. With the manifest's `memory: off` (sb-tenant(5)) the cell keeps and sends none: the calls answer `on: false`, and adding a line is `EUNAVAIL`. The web UI's Questions tab has **About me** with the lines, **Add** and **Remove**, and each answer has **Remember something about me**, an empty field: the answer's text is never put in it.

### Context for the work (SB-4304 to SB-4307)

**Collections** (SB-4304). A collection names the documents and saved questions for one piece of work, so each ask doesn't have to find them again. `GET /v1/collections` lists those the caller owns or that are shared with them, newest first: `{ "items": [{ "id": "col_…", "name", "owner", "mine", "items": [{ "item", "title"? }], "hidden": N, "shared": [EMAIL…]?, "at", "stale"? }] }`. `POST /v1/collections` `{ "name": "…", "items": ["KIND:ID", "sq_…"], "shared": [EMAIL…] }` makes one: a name of 1 to 120 characters, at most **50** items, each a document as `KIND:ID` (a version is dropped) or one of the caller's own saved questions (`sq_…`), and at most 20 people to share it with, each one active user now (LAW-12). `PUT /v1/collections/{id}` replaces its name, items and shared people; `DELETE /v1/collections/{id}` removes it. Only its owner may change or remove it (`EPERM`); anything else malformed is `EINVAL`. A collection keeps **ids only**: never a document's title or text. **Each reader sees only what they can open**: every time it is listed, its documents are checked live as the reader, and the ones they can't open are counted in `hidden`, never named (LAW-01); a saved question shows its question to the owner and to the people it is shared with, as a share does, and one its owner removed is gone. `shared` is shown to the owner only. **Ask this collection** sends `collection` with an ask (Request, above). A collection no one asked about for 90 days carries `"stale": true` for its owner, and the Collections screen offers to remove it; nothing is removed for them. Each change is audited (`access`, `collection`, the collection's id and the SHA-256 of its items, never a title). Asking it, or changing it, marks it used. Collections are in **Download my data** (`collections`) and erased with their owner; they are never expired by retention.

**What agents did as me** (SB-4305). `GET /v1/me/agent-runs` lists every run an agent made **as the caller** in the last 90 days, newest first: `{ "items": [{ "kind", "agent", "space", "at", "title", "read": [{ "cite", "title" }], "hidden": N, "drafted": "…", "link" }] }`. A run is a scheduled or triggered agent's draft made as them (sb-agents(7), Scheduled and triggered agents), and each of their research reports, meeting briefs, routines and suggested fixes. `read` is what the run read: the documents its traces allowed, each checked again **as the caller now**, so only titles they can open are named and the rest are counted in `hidden` (LAW-01). `drafted` says what it made: the draft's title, or the report's question, and how many claims. The list is drawn from the traces, the steward queues and the stored reports, as they are kept (sb-tenant(5), Retention): **no new record is kept**, so a run whose traces have expired shows `read` empty. The web UI's Inbox tab has **Agent runs**.

**Numbers from tables** (SB-4307). A model asked to add up a sheet gets the arithmetic wrong, so the `ask` agent does it in code. When a question asks for a number (how many, how much, a total, sum, average, mean, count, minimum, maximum, highest, lowest, largest, smallest) and what the live check allowed holds a spreadsheet (an `.xlsx`, `.ods` or `.csv` document, sb-ingest(7), Spreadsheets), the agent makes one more model call with the bundled `table` prompt: the model sees the question and, as data, each such sheet's name and first row (its column names), never its other rows, and answers with at most one plan: `{ "doc", "sheet", "where": [{ "column", "equals" }], "op", "column" }`, `op` one of `count`, `sum`, `average`, `min` and `max`, at most 3 filters. Anything else, or no plan, and the answer is composed as without the tool. The **table tool** then runs in code: it reads every stored chunk of that version of the document, checked **as the asker** as any chunk is (LAW-01), rebuilds the sheet, keeps the rows where each filter's column equals its value (ignoring case and spaces at either end), and computes `op` over the column (`count` counts the rows; the others read numbers, a cell that isn't one is skipped). It reads only, writes nothing and calls nothing. Its result goes to the composer first among the sources, as a passage of that document with the document's own cite: "Table tool result: sum of Amount where Customer is acme-logistics, over Invoices!C2:C41: 12840.5 (12 rows)". The range counts the rows the index holds (a row with no value isn't one), the first being the column names. The answer carries it as `table`. **The composer check** (LAW-14): a claim that cites a spreadsheet and states a number that is neither in the text of the passages it cites nor the tool's value is **dropped**, counted in `dropped`. When the document isn't whole in the index, or a column isn't found, the tool returns nothing and the answer is composed without it.

### Requests to a department, exactly (SB-4104)

A space with `requests` (sb-space(5)) takes requests from its members. `GET /v1/spaces/NAME/requests` gives a member `{ "space", "categories": [...], "due_days" }`, with no categories for a space that takes none. `POST /v1/spaces/NAME/requests` `{ "category", "text" }` sends one: the category is one of the space's, ignoring case, and the text 1 to 4000 characters, as a question. It returns `{ "id", "to", "category", "due" }`. The request is a question to the space's stewards (Questions to the stewards, above) with `request: { "category", "due_days", "due" }`: `due` is the end of the day `due_days` working days after it was sent, in the `digest` time zone. It needs no answer first, and it is audited like a question (`asked`, reason "request to stewards", the text hashed). Claims, replies, notes and notifications work as for any question. On the asker's `GET /v1/questions` and the steward queue it carries `request`, and the queue marks it `overdue` once `due` has passed. **Past due it climbs**: a request takes each step up the tree (Up the tree, above) after its `due_days`, not 10, and the queue it reaches is told "1 request went past its due date in a team" (or "in its space" for the company-wide answerers): counts only, never its text or category. The brain routes and records a request; it never does it. A non-member is `EPERM`; a space without `requests`, an unknown category or no stewards is `EINVAL`.

### Asking for access, exactly (SB-2205)

Where an answer or a search counts sources the asker can't open, `POST /v1/access-requests { "trace": "tr_…" }` asks their owners to share them. The trace must be the asker's own, from the last 7 days. Only sources **the source itself refused** (`source_denied` in the trace's decision list) are asked about: one refused by a space, label or barrier check isn't, since sharing it at the source wouldn't open it, and a request across a barrier would tell the other side what was asked (LAW-22). For each such document, at most 20, the cell finds its owner at the source as for who to ask (exactly one active directory user with the email, else nobody), and sends that owner one `access` notification (Notifications, below): the asker's email and the document's title, which the owner can open, and never the question or the answer (LAW-07). It sends **one request per asker, document and week**; asking again that week sends nothing more. The response is counts only: `{ "sent": 2, "already": 1, "no_owner": 1 }`, never which documents or who, so the asker learns nothing they didn't know (LAW-01); someone already named in the answer's `people` is still named there. An owner who has turned `access` off gets nothing, and the asker isn't told. A cell with no chat bot and no `email` to send from is `EUNAVAIL`. The web UI shows **Ask the owners for access** under "N sources were not shown", and then the counts.

An address the server refuses (`550`) is skipped like someone the chat doesn't know. A cell with none of the three sends nothing, and the job still runs and finishes. Slack's bot needs `chat:write`, `im:write` and `users:read.email` for this; Mattermost's bot needs to be able to create direct channels.

`GET /v1/traces/{id}` returns the same answer plus the decision list (`cite`, `verdict`, `reason`, one per candidate document), for the user who asked and for auditors. Anyone else gets `EPERM`, the same as an unknown id. `reason` is one of `allowed`, `source_denied`, `source_unknown` or `policy_denied`, and in a cell with spaces `space_denied` (not held by the space asked in), `label_denied` (a `confidential` or `restricted` chunk held only by spaces the asker isn't in) or `barrier_denied`. `POST /v1/feedback` takes `{ "trace": "tr_…", "rating": "up"|"down", "wrong_citation": "docs:…@17"?, "outdated_citation": "docs:…@17"?, "comment": "…"? }` (SB-310, SB-2703):

| Rule | Detail |
|---|---|
| Who | Only the user who asked. Anyone else, or an unknown or expired trace, gets `EPERM` |
| `rating` | Required, `up` or `down` |
| `wrong_citation` | Optional. It must be a citation **in that trace's answer**, or the request is `EINVAL` |
| `outdated_citation` | Optional (SB-2703): a citation in that trace's answer that the reader found **out of date** rather than wrong, with the same rule. It puts the document on its spaces' review list, and is never turned into an eval case, because the cite wasn't wrong when it was made |
| `comment` | Optional, at most 2,000 characters |
| Repeats | One feedback per trace: a later one replaces the earlier one |
| Response | `200 { "trace": "tr_…", "stored": true }` |

Feedback is stored against the trace id with the release, and exported weekly (Monday 00:00 UTC, the previous seven days) as JSON lines for the pilot review. Each line holds the trace, release, rating, wrong citation, outdated citation, comment, time, and the answer's claim, uncited and refused counts, but never the question or the answer text. Reviewers who need those open the trace with auditor rights. Operators see every unhelpful answer in the console's queue, `GET /v1/admin/feedback?rating=down` (sb-admin(3); SB-1609), with the same counts, the trace's policy decisions and the asker's comment, and mark each one reviewed. A later feedback on a reviewed trace puts it back in the queue.

### The web UI

On GCP the web UI is served from a Firebase Hosting site in the cell's own project, which rewrites `/v1/` to that cell's `api` only (sb-runtime(7), Web UI hosting).

The cell serves its web chat UI at `/` on the tenant's own hostname, from the release's built assets (SB-307). | Notifications | The Questions tab ends with "Tell me in chat about": a checkbox each for replies to the person's questions, new questions for spaces they steward, the weekly digest and watched questions, saved with `PUT /v1/me/notifications`, and **Pause for** 1 to 30 days, or **Resume** while paused (SB-2506), and **Send me a test** (SB-2602). `/?tab=questions`, the link replies are told with, opens the app on that tab |
| Save and share | Each answered turn has **Save** and **Share**. Share shows the `/q/sh_…` link to copy. The Saved tab lists saved questions; opening one asks it again |
| Watch | Each saved question in the Saved tab has a **Watch** checkbox (`PUT /v1/saved/{id}/watch`). `/?tab=saved` and `/?tab=documents` open the app on those tabs |
| Copy | Each answer has **Copy** and **Copy as Markdown** (SB-2401): the question, then each claim followed by the numbers of its cites, then the cites, numbered, with title and link (a cite with no `url` is its `cite`). An uncited claim is copied with the screen's word "Uncited" in front, hidden sources only as the screen's "N sources were not shown" line, and nothing else: no owner, trace or snippet beyond what the answer shows |
| Print | **Print** opens the browser's print dialog, where Save as PDF makes a file (SB-2402). The print stylesheet leaves out the tabs, the ask form and every button, and prints the question, the answer with "Uncited" where the screen has it, and the cites as numbered footnotes with their links and ages; nothing is rendered on the server |
| Keyboard | (SB-2403) A "Skip to the conversation" link comes first. `/` moves focus to the ask box, Ctrl+Enter (Cmd+Enter on a Mac) in the ask box asks, and Esc closes the API tokens panel and returns focus to its button. None fires while focus is in a field, except Ctrl+Enter in the ask box. A line under the ask box lists them |
| Recent questions | (SB-2405) Under the ask box, **Recent questions** lists the person's last 20 questions, newest first, each a button that puts it back in the box, and **Clear**. They are kept **in that browser only** (`localStorage`), never sent to the cell for this, so the cell keeps no more question text than before (LAW-07). They are cleared by **Clear**, by **Sign out everywhere**, and when the cell says the person is signed out (`EAUTH`). A shared question (`/q/sh_…`) asked from its link isn't added |
| No dead ends | (SB-2406) A search with no results, or an answer whose `notice` is `no_sources` or `no_access`, offers next steps: **Search the whole company** (or **Ask the whole company**) when it was in a space, **Clear filters** when a filter was set, **Ask it as a question** from Documents, and **Ask the stewards** under an answer (as above). Which appear depends only on what the person typed and chose, never on the index: a document the person can't open changes none of them (LAW-01). Glossary terms the question used are shown as everywhere (Glossary, exactly) |
| Stewards' tools | On the steward screen (SB-2501 to SB-2503): **Reviewed, still right** on each document to review, **I'll answer this** and **Let it go** on each open question, "ann@… is answering" on a question someone else claims, and **Use a template** with the space's templates over the reply box, which a steward can add to, edit and remove. The Questions and Documents to review headings say how many wait, read on load and every five minutes (SB-2504), and **Download CSV** saves the review list as shown, made in the browser (SB-2505) |
| Keep the good replies | (SB-3401 to SB-3404) An answered question has **Publish as note** with a title and **Keep the question in the note**, off by default. An open question shows **Overdue** from 5 working days, **Looks like qs_…** when it matches another question of the queue, with **Answer both** beside **Send reply** while that one is open, and, on the company-wide queue, "finance hasn't answered this in 10 working days" |
| Your data and sessions | (SB-3501 to SB-3503) The Questions tab ends with **Your data**: **Download my data**, which saves `GET /v1/me/export` as `my-second-brain-data.json`, and **Forget my questions**, enabled only once the person types "forget my questions", which says how many records a legal hold kept. The foot of the page has **Where I'm signed in**, read when it is opened: each session and API token with when it started, the day it was last used and when it ends, **This browser** on the current one, and **Sign out** on each |
| Retire and tidy | (SB-2801 to SB-2804) Each document to review has **Retire from answers**, which asks for a reason and, optionally, the replacement's `KIND:ID`; **Retired** lists the space's retirements with **Bring back**. The list also shows **Same name, different text** groups, notes whose sources moved, and **Never cited** on request, each with **Retire from answers**, with the glossary terms no question used (SB-2805). Above the list, **Answers resting on stale sources** shows this month's share and last month's (SB-2807). A citation chip of a replacement says **Replaces OLD TITLE** |

The UI renders a claim only as cited (with at least one chip) or as uncited, never as plain text (LAW-14). It targets WCAG 2.2 AA: everything works by keyboard, focus is always visible, the answer area is an `aria-live` region, and every chip has an accessible name that includes the cite.

`cites[].url` is set when the source's connector can link to a version; it is omitted otherwise. `agent` names the agent that answered, and `dropped` counts the uncited claims a department agent left out, always 0 for `ask` (sb-agents(7), Department agents). In a cell with spaces, `cites[].spaces` names the spaces that hold the cited document and `cites[].label` its label (sb-spaces(7)); both are omitted in a cell without spaces (SB-1007).

### Your own data (SB-3501, SB-3502)

| Endpoint | Does |
|---|---|
| `GET /v1/me/export` | (SB-3501) A JSON file of the caller's own records: `{ "user", "records": { "traces", "conversations", "feedback", "saved questions", "shares", "steward questions", "notification settings", "memory" }, "tokens": [{ "name", "created", "expires" }], "left_out": N }`, the same selection as the operator's export (sb-admin(3), SB-1903) with `user` the caller. Each trace is only `{ "id", "at", "space", "answer": [{ "text", "cites" }] }` (the questions are in `conversations`), with every cite checked again as the caller now: a cite they can no longer open is left out, a claim left with no cite is left out, and `left_out` counts both. A steward question's reply keeps only the cites they can open now, never the steward's name or what it looks like (SB-3402), and a feedback's reported cite is kept only if they can open it now. Records the person made as a steward (eval cases, review marks, templates) are in the operator's export only. Audited as the export is (`retention`, `export:USER`, counts and the file's SHA-256, never its text). The Questions tab has **Download my data** |
| `POST /v1/me/forget` `{ "confirm": "forget my questions" }` | (SB-3502) Erases the caller's own traces, conversations, feedback, saved questions (and their routines) and their shares, and their memory (SB-4303), any age, through the retention stores (sb-tenant(5), Retention and deletion). A different `confirm` is `EINVAL`. A record a legal hold covers is kept (SB-1207): `200 { "erased": { "traces": 12, … }, "held": 3 }`, and the audit rows (`retention`, `forget:USER`, `requested` then `done`) hold the counts only. Questions sent to stewards, eval cases and settings stay; the operator's erasure removes those. The Questions tab has **Forget my questions**, which asks the person to type the phrase |

### The notice to everyone (SB-3207)

While an admin's notice stands (sb-admin(3), `PUT /v1/admin/notice`), the web UI shows it at the top of every screen, read from `GET /v1/notice` on load and every five minutes, and the chat apps put it as the first line of every answer, `Notice: …`. It is shown as plain text, never as a link or markup, and it is gone once its end time passes.

### Spaces

`GET /v1/spaces` lists the spaces the asker is a member of, now, as `{"spaces": [{"name": "finance", "label": "restricted"}]}`, sorted by name. Spaces the asker isn't in are never listed, and a cell without spaces returns an empty list. A registry that can't answer is `EUNAVAIL`.

### The chat app (Slack)

Staff can also ask from Slack with `/ask <question>` (SB-308). It is the same `ask` agent with the same laws. Only the entry point differs: Slack calls `POST /chat/slack/commands` for the command and `POST /chat/slack/interactions` for the Share button.

1. **Verify.** The cell checks Slack's request signature with the signing secret from `vault://tenants/TENANT/connectors/chat` and refuses any request older than 5 minutes. The `team_id` must be the tenant's workspace. Anything else gets HTTP 401 and no reply.
2. **Map the person.** The bot looks up the Slack user's email (`users.info`) and finds the **one active** directory user with that email (SCIM-provisioned, sb-identity(7)). No match, more than one match, or an inactive user gets an ephemeral reply saying the account can't be matched, and **no answer**. The bot never falls back to a shared or service identity.
3. **Answer privately.** Slack gets an immediate ephemeral "Looking that up…". The answer follows through Slack's `response_url` (only `https://hooks.slack.com/`), also **ephemeral**, so only the asker sees it. The stale and sync warnings (`notice_stale`, `notice_sync`; SB-2701, SB-2704) come first, in the web UI's words. Claims show as text with their citations as links (`<url|cite>`). Uncited claims start with *Uncited:*. The reply ends with who to ask (the answer's `people`, each with the documents of theirs it cites), the notice, the refused count and the trace id.
4. **Spaces.** In a cell with spaces, the channel the command was typed in picks the space: a space's `channels` in the manifest (sb-space(5)) list the channels that ask in it. A mapped channel asks in that space, and someone who isn't a member gets an ephemeral reply saying so and **no answer**, never a company-wide one. An unmapped channel, or a direct message, asks company-wide.
5. **Share.** A *Share in channel* button posts the question and the **citation links only, never the claim text**, so each reader opens the sources under their own access. Only the asker can share, and the trace is read again with the asker's own scope.

6. **Save to the brain** (SB-3703). A message shortcut, *Save to the brain* (callback id `save_to_brain`, through `POST /chat/slack/interactions`), sends the thread the message is in to the stewards of the channel's space (or `questions_to` company-wide), as a saved thread in their queue: who saved it, a link to it, and at most 50 of its messages, each as `EMAIL: text` with the author mapped by `users.info`, 4,000 characters in all. The cell reads the thread with the bot's token (`conversations.replies`). Only someone mapped to one active directory user can save one, and in a space's channel only a member; each save is audited (`access`, state `saved`, the SHA-256 of the text). Nothing is published: a steward's reply and **Publish as a note** publish it, or **Discard** drops it. The person gets an ephemeral "Sent to the stewards of NAME."

Errors are ephemeral replies with the error's `message` and trace id. Slack scopes for the bot: `commands` for `/ask`, which answers through `response_url`, `channels:history` and `groups:history` for *Save to the brain*, and `chat:write`, `im:write` and `users:read.email` for notifications (Notifications, above), which are direct messages that never carry an answer.

### The chat app (Mattermost)

Sites that run their own Mattermost can ask from it with a slash command (SB-2005), for example `/brain <question>`. The command is a Mattermost **custom slash command** whose request URL is the cell's `POST /chat/mattermost`, method POST; the cell takes it when sb-cell(5) sets `mattermost.base` and `mattermost.team_id`. It follows the Slack app's rules, from the same code:

1. **Verify.** The command's token (the form's `token`, or `Authorization: Token …`) must equal `command_token` in `vault://tenants/TENANT/mattermost`, read at every request, and `team_id` must be the tenant's team. Anything else is HTTP 401 and no reply.
2. **Map the person.** The cell reads the Mattermost user's email with the bot's token (`bot_token` in the same secret; `GET /api/v4/users/ID`), and finds the **one active** directory user with that email. A deleted Mattermost user, a bot, a hidden email, no match, more than one, or a deprovisioned user (LAW-12) gets an ephemeral reply that the account can't be matched, and **no answer**.
3. **Answer privately.** Mattermost gets an immediate ephemeral "Looking that up…", and the answer follows through the command's `response_url`, which must be the server's own `/hooks/commands/` URL, also **ephemeral**. It is Markdown: the question, the stale and sync warnings in the web UI's words (SB-2701, SB-2704), each claim with its citations as links (`` [`cite`](url) ``), uncited claims marked *Uncited:*, who to ask, the notice, the refused count and the trace id. Claim text is escaped, so it can't become a link, a mention or formatting.
4. **Spaces.** A space's `channels` (sb-space(5)) list Mattermost channels by name as they do Slack's: a mapped channel asks in that space, and someone who isn't a member gets an ephemeral refusal, never a company-wide answer.

5. **Share** (SB-2105). The answer carries a *Share in channel* button, a message attachment action whose integration URL is the cell's `POST /chat/mattermost/actions` (sb-cell(5) `base_url`). Its context holds the trace id, the asker's Mattermost user id, the command's `response_url` and an HMAC-SHA256 over the three keyed with `command_token`; Mattermost doesn't sign action requests, so the cell checks that HMAC with the token read at the press, and anything else is HTTP 401. Only the asker can share: the pressing `user_id` must be the one in the context, mapped again to the one active directory user, and the trace is read again with that scope. The channel then gets, through the `response_url` as `in_channel`, the **citation links only, never the claim text**, exactly the Slack rule, so each reader opens the sources under their own access. Anyone else pressing it gets "Only the person who asked can share this answer." `response_url` lasts 30 minutes, so a later press says the answer can't be shared any more.

6. **Save to the brain** (SB-3703). `/brain save LINK`, with a message's permalink (or its post id) and typed in the same channel, sends that message's thread to the stewards of the channel's space, as Slack's message shortcut does (above): the same mapping, limits and audit. The cell reads the thread with the bot's token (`GET /api/v4/posts/ID/thread`) and refuses one from another channel than the command's, so nobody saves a thread they weren't in. `/brain save` alone explains how; any other text is a question.

The bot account needs to read users' emails (the System Console's *Show Email Address* for it) and to create direct channels for notifications (Notifications, above); replies and shares go through `response_url`.

## ERRORS

| Code | When |
|---|---|
| `EINVAL` | Missing or over-long `question`, an unknown `sources` kind, or a `conversation` that isn't the user's |
| `ESPACE` | `?space=` names a space the cell doesn't hold or the asker isn't a member of (never asked company-wide instead) |
| `EINVAL` (agent) | A department `agent` asked company-wide, in a space of another template, or not enabled by the manifest or the space |
| `EAUTH` | Not signed in, or session revoked |
| `ETENANT` | Token is for another tenant |
| `EKILLED` | `ask` agent or the tenant is killed |
| `EBUDGET` | Budget or rate limit reached |
| `ERATE` | The asker's `asks_per_minute` is used up; `retry_after` says how many seconds to wait (SB-2305) |
| `EUNAVAIL` | Index or model unavailable (never falls back to anything shared) |

A refused source is **not** an error. The answer reports it through `refused` and `notice`.
