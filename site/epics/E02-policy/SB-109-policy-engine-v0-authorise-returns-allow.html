SB-109: Policy engine v0: authorise returns allow, deny or unknown

Field Value

Stories US-02.1

Status In review

Why

The kernel has one entry point and three answers; unknown is never allow.

Acceptance criteria

  • ✓authorise(principal, action, resource, context) returns Allow|Deny|Unknown with a reason
  • ✓Every caller maps Unknown to refusal; a lint forbids switch statements that fall through on Unknown
  • ✓LAW-03 green over mocks (policy level; retrieval level is SB-302)

Subtasks

  • ✓Update the man pages listed above first (manual first, P2)
  • ✓Define policy.Decision type
  • ✓Cedar evaluator adapter
  • ✓Caller helper policy.Require
  • ✓Custom lint for Decision handling
  • ✓LAW-03 fault-injection tests
  • ✓Write or extend the law tests: LAW-03
  • ✓Devlog entry, ledger and changelog updated

Progress

2026-11-19: built. - internal/core/policy: Decision (the zero value is Unknown) and Authorise(scope, action, resource, context). It builds the principal only from the tenancy.Scope, denies other-tenant resources before any policy runs, and runs the engine with a 50 ms deadline and panic recovery. Anything but a clean Allow or Deny is Unknown, always with a reason. Require returns nil only for Allow. - internal/adapters/policy/cedar uses cedar-go v1.8.0 (ADR-0017; vendored now). Policy evaluation errors become Unknown. Tests run the platform base.cedar through the real kernel. - tools/check/decisions.py (run by make lint, with a built-in self-test) refuses != policy.Deny and default: in Decision switches. exhaustive requires the Unknown case.

LAW-03 gains TestLAW03_PolicyUnknownRefuses, red first, then green. It injects engine errors, timeouts, panics and invalid values, plus other-tenant resources and missing scopes. A "not denied means allowed" caller is caught.

Left: a second reviewer. Changes to policy and audit need two (definition of done); the user reviewed on 2026-11-19, and CI is green.
