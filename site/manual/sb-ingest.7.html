sb-ingest(7)

NAME

sb-ingest — how source content becomes searchable, and stays data

SYNOPSIS

Changes → Fetch → normalise → sanitise → chunk → provenance → embed → index

DESCRIPTION

Read-only by default

Connectors use read-only scopes unless a gated workflow needs write access to that connector. Paths and channels listed in exclude are never fetched.

Freshness

Changes, including deletes and permission changes, are indexed with a p95 of 15 minutes or less. A delete removes all of the document's chunks at the next sync; the source's change feed is the tombstone record, so nothing else is kept. A permission-only change re-ingests the same version, so the prefilter matches the source again. In the gap, the live ACL check still protects every answer (LAW-01): the prefilter only narrows candidates and never grants.

Sync

Each connector of a cell is synced by a scheduler every 60 seconds, with up to 10 seconds of jitter. One sync reads the connector's changes from its stored cursor, ingests them, and only then stores the new cursor. If anything fails, the old cursor stays, so the next run repeats the work. Ingest is idempotent, so repeating it is harmless. A cell restart resumes from the stored cursors and never from the beginning; a cursor that was never stored, or was lost, starts from the beginning, so nothing is skipped. The ingest service (sb-ingest, or sb-api --with ingest; sb-runtime(7)) re-routes every connector's documents to the current spaces before its first sync, runs each connector in its own loop, and backs a failing connector off (one minute, doubling, at most 15 minutes) without slowing the others. When a connector's last success, or the service's start if it has none, is more than 15 minutes old, it sends one ingest_stale alert (Sev-2) until the connector succeeds again. Secrets and fields dropped at ingest are counted in sb_ingest_secrets_dropped_total{connector, pattern} and sb_ingest_fields_dropped_total{connector, field}.

On GCP that scheduler is Cloud Scheduler, every minute, and a missed run alerts (sb-runtime(7), Schedules).

First syncs (SB-6004). Every sync reads at most sb-cell(5) sync.max_per_minute documents a minute (default 600). A source's 429 is waited out, never a failure: the sync waits the source's Retry-After (or 1, 2, 4… seconds, at most 5 minutes) and reads the same document again, up to 8 times before the sync fails as rate_limited; each wait counts in sb_ingest_throttled_total{connector}. A connector's first sync (no cursor yet) keeps a checkpoint, at the start and every 500 changes, beside its cursor (CONNECTOR--first): a sync stopped by a failure or a restart resumes from the last checkpoint and reads nothing before it again, since a connector lists a first sync's changes in the same order each time. The checkpoint goes when the cursor is kept. Health shows the first sync's progress (first_sync, sb-admin(3)), and answers from a space that reads the connector say it is still indexing (notice_indexing, sb-ask(3)).

A changed document is ingested as a new version, first seen at that sync; a rebuild's versions are never new (Rebuild). In a space with on: [source-changed] (sb-space(5)), a new version of a document an agent draft drew on redrafts that draft for review, once a day at most, and republishes nothing (SB-4905; sb-agents(7), When a source changes).

Freshness is measured per connector as the age of the last successful sync, exported as sb_ingest_last_success_age_seconds{tenant, connector}. It stays well under the 15-minute target while syncs succeed, and an alert fires when it passes 15 minutes. Failures are counted in sb_ingest_sync_failures_total{tenant, connector}.

Content is data

Ingested text is written by people who aren't the asker, and some of it may be hostile. The sanitiser:

  1. strips hidden text (zero-width characters, off-screen or white-on-white styling, comments, alt-text payloads);
  2. flags spans that look like instructions to an AI;
  3. at prompt time, wraps every chunk in a quoted data block with its provenance.

Tool arguments derived from flagged spans are refused by the tool bus (LAW-09). Flags show on citations, so users can see when a source contained suspicious text.

The rules, in order (internal/core/ingest, Sanitise):

Step Rule Recorded as
Strip Zero-width characters, bidirectional controls and other invisible format characters; HTML comments; elements styled display:none, visibility:hidden, font-size:0 or positioned off-screen; image alt text and link titles longer than 100 characters flag hidden_text_removed
Flag Text addressed to an AI: overrides ("ignore previous instructions", "disregard the above"), new roles ("you are now", "act as"), chat-role markers (system:, assistant:, <|im_start|>), tool-call syntax ({"tool": …}, function-call JSON), requests to hide things from the user, and links that carry data in their query string to a domain outside the tenant flag instruction_like
Wrap At prompt time each chunk becomes <<data cite="…" flags="…">> … <</data>>. Any << or >> inside the text is escaped first, so content can't close its own block —

A spreadsheet's cells are content like any other (SB-2206): a cell that reads like an instruction is flagged, and a formula is never evaluated, only the value the file last saved is read, so a cell can't make ingest compute, fetch or run anything (sb-connector(3), docs: folder).

Flags are per chunk and appear on its citation. A flagged chunk is still indexed and found by search.

Suspect passages (SB-5101). At read time, before a model sees it, every passage is checked again: a chunk flagged instruction_like, or whose text matches the instruction rules as they are now (so a chunk indexed before a rule was added is caught too), is suspect. By default a suspect passage is skipped: it never enters a prompt, is never quoted or cited, and the answer says how many were skipped (skipped in sb-ask(3)). Its cite is kept in the trace, never its text. This holds on every path that gives passages to a model: answers and department agents, research, briefs and drafts (they answer through the same composer), and tables (SB-4307). A space with suspect: monitor (sb-space(5)) lets suspect passages through as before, wrapped and flagged, and still records them. Stewards see the space's suspect documents on the review list (section=suspect, sb-ask(3)), and each document's owner is told once per document version. Hidden text that was stripped (hidden_text_removed) doesn't make a passage suspect: what's left is what a reader sees. The corpus in evals/corpus/injection.json (visible, hidden and benign look-alike cases) runs in make check. The agent-level injection suite (zero tool calls from poisoned sources) runs once the tool bus exists (SB-405, SB-501).

Nothing sensitive goes out (SB-5102)

Ingest keeps credentials out of the index and masks personal data in what a model reads, but text can still reach someone another way: a model's own words, a steward's reply, a note, a file someone asked about, a notice. So one filter sits on every way text leaves the cell:

Way out Where the filter is
Every API response: answers, drafts, briefs, search, reviews, exports, MCP results, the web app's data the cell's HTTP handler masks every JSON string and every CSV, Markdown or plain-text body
Notices, digests and briefs sent as chat messages or email the notify job, before each message is sent
Chat app replies (Slack, Mattermost) the chat app, before each reply is posted

It replaces each credential the secret scanner knows (Secrets never stored, below) with [removed], and masks each payment card, IBAN and national id but its last four characters, as Personal data does. The rest of the text, and every cite, are left as they were, so an answer with one masked number is still the answer. Two things pass as they are: POST /v1/tokens, which shows the caller their new token once, and GET /metrics, which holds numbers only. Masking can't be turned off, and each masked response or message is a guardrail event (sb-observability(7), Guardrail events). Each way out has its test (LAW-07): the API's (TestMaskOutMiddleware), the notify job's (TestMaskingSender) and each chat app's (TestReplyIsMasked), and a running cell gives back a key and a card number a person saved masked (TestGuardWhatGoesInThroughARunningCell).

Fields (SB-1106)

For a document that arrives as fields (sb-connector(3), Fields), ingest builds the text itself, before chunking, from the fields that are allowed:

  • a declared field that isn't sensitive is allowed;
  • a declared sensitive field is allowed only if the fields allow-list of a space that holds the document names it (sb-space(5)), and then the document is labelled restricted, whatever its source or space would say (LAW-20), and is held only by the spaces that allow every sensitive field it carries, so another space holding the same record never reads them. If no holding space allows them all, only the sensitive fields every holder allows go in (SB-1401);
  • a field the connector didn't declare is never allowed.

Every other field is dropped: its value is never chunked, embedded, indexed or logged. The sync reports the dropped fields by name and count only, as sb_ingest_fields_dropped_total{tenant, connector, field}. The text is the document's title, then one Name: value line per allowed field, in the order the connector declares them. A document that arrives as fields from a connector that can't declare them isn't ingested at all, and is counted as undeclared, so a source that can't say what it holds never feeds a restricted space.

Secrets never stored (SB-1103)

Every chunk of every connector passes a secret scanner before it's embedded or written, and so does the whole document first, so a secret a chunk boundary splits (a private key longer than a chunk) is found in every chunk it touches (SB-1401). A chunk that holds or touches what looks like a credential is dropped: a private key block from header to footer, a cloud access key, a GitHub, GitLab, Slack, Stripe or model-provider key, a Second Brain API token (sbt_…, SB-2306), a JWT or bearer token, credentials in a URL (postgres://user:pass@host), or an assignment to a name that says it is a secret, such as password = "…", aws_secret_access_key=… or token: …, with a long value, quoted or not. A dropped chunk is it is never embedded, indexed or logged, and sb_ingest_secrets_dropped_total{tenant, connector} counts it. The rest of the document is indexed as usual. Only the chunk's id and the pattern's name reach the trace of the sync, never the match (LAW-07).

Sharing at sync (SB-5401, SB-5403)

A document that had a chunk dropped for a secret keeps the fact on its other chunks, flagged secret_removed: never the secret, never which chunk. Each sync also compares a document's ACL copy with the one indexed for its last version. A change is kept as a sharing event, the grants added and removed and never content; a widening is a group, a domain or anyone added (a person added by name is not one). Its owner is told once (notify kind widened), or, when the owner can no longer open the document at its source, the stewards of the spaces that hold it. A narrowing is recorded but not announced. A sensitive document that widened stays on the review list's wide section for 30 days (sb-permissions(7), Shared too widely). Ingest never changes a source's sharing.

Personal data (SB-1904)

Ingest also looks for personal data in every document: an IBAN whose check digits are right (ISO 13616, mod-97 = 1; 15 to 34 characters, grouped in fours or not) and a payment card number (13 to 19 digits, spaces or dashes between groups allowed) that passes the Luhn check and starts with a prefix a card network issues (Visa, Mastercard, American Express, Discover, JCB, Diners). From SB-2207 it also finds four national identity numbers:

Number Written as Valid when
UK National Insurance number AB123456C or AB 12 34 56 C, capitals Two prefix letters (the first not D, F, I, Q, U or V; the second not D, F, I, O, Q, U or V; never BG, GB, KN, NK, NT, TN or ZZ), six digits, and a suffix A to D
US Social Security number 123-45-6789 or 123 45 6789 The area is not 000, 666 or 900 to 999, the group not 00 and the serial not 0000. Nine digits with no separators aren't read as one
Dutch citizen service number (BSN) 123456782 or 1234.56.782 Nine digits that pass the 11-check (9·d1 + 8·d2 + … + 2·d8 − d9 is a multiple of 11, and not all zero)
German tax id (Steuer-IdNr) 86095742719 or 86 095 742 719 Eleven digits, the first not 0; in the first ten one digit appears two or three times (three never in a row) and every other at most once; the last is the ISO 7064 MOD 11,10 check digit

A number with wrong check digits, one that breaks its format's rules, or one inside a longer word or number, isn't one. A nine-digit number that happens to pass the 11-check, about one in eleven, is read as a BSN and masked: the scanner errs towards masking. Each chunk that holds a number, or part of one a chunk boundary cut, is flagged personal_data. Unlike a secret, it is indexed and can be cited: a payroll sheet is still a document people need. But nobody reads the whole number through Second Brain: a flagged chunk's search snippet, and the text the model is given to answer from, show each number masked but its last four characters, with separators kept (•••• •••• •••• •••• ••30 00), and every answer's text is masked the same way before it is returned or stored. The flag is derived from the text, so a rebuild gives the same flags (LAW-13). The space's stewards see how many documents in the space carry it (sb-ask(3), the review list), as a count, never which. The detectors have a fuzz target (FuzzMaskPII): a masked text never still holds a number, and keeps its length.

Provenance

Every chunk records tenant, cite (kind:id@version), span, content hash, flags and the release that ingested it, and, from SB-1701 to SB-1708, the document's title and location and when the index first saw this version (seen). Ingesting the same version again keeps the first seen; a new version gets the time it was first ingested. That time is what search shows as a document's age, what "what changed" lists (sb-ask(3)) and what the stewards' review list measures staleness by.

Every chunk also carries the text hash of its document (SB-2202): the SHA-256 of the document's normalised text, without its title, the same on every chunk of the version and empty for a document with no text. Two documents with the same text, in two places or under two names, have the same hash, which is how the stewards' review list finds copies and how answers cite one copy (sb-ask(3)). Like every field of a chunk it depends only on the source, so a rebuild gives every document the same hash again (LAW-13). The hash is of the text, never the text itself, and never logged.

Review-by dates (SB-2705)

A document can say when it should be reviewed or when it expires. Ingest reads one date: review-by: (or review_by:), else expires:, from a Markdown document's front matter (the lines between a first line --- and the next ---, in its first 4 KiB), or the custom property review-by (else expires) of a .docx or .pptx file, read from docProps/custom.xml only. The date is YYYY-MM-DD or RFC 3339, in UTC. Every chunk of the version keeps it as review_by, and a rebuild reads it from the source again (LAW-13). A cite is stale from that date, or from its age past review_after_days, whichever comes first (sb-ask(3), Documents to review), and a Reviewed, still right mark doesn't lift it: the document itself says it is due, so its owner updates it. The date is data, so it can only make a document stale sooner, never fresher (LAW-09): a date in 2099 changes nothing. A steward's note (sb-ask(3), SB-1705) is written with review_by: 180 days after it was published, and a republish writes the date again: the connector rewrites a note only when everything after its front matter is the same (SB-3403). A value that isn't a date is ignored and counted in sb_ingest_review_by_ignored_total{connector}, never the value.

Goals (SB-4101)

A goal is a Markdown document whose front matter (as in Review-by dates, above) says type: goal, with owner: EMAIL, quarter: YYYY-Qn, status: one of on_track, at_risk, off_track or done, and, optionally, parent_goal: the title or source id of a goal in the space above. A goal without a valid quarter or status is indexed as an ordinary document and listed as no goal. The fields are read at query time from the document's first chunk; nothing about a goal is stored apart from the document, so a goal is checked like any document (sb-ask(3), Goals, updates and policies). A goal that waits on another department says so with waiting_on: SPACE, waiting_reason: (one line) and waiting_until: YYYY-MM-DD, read the same way; it is cleared by removing them (SB-4504; sb-ask(3), Work across departments).

Action items (SB-4203)

A meeting transcript's action items are read from its text when its decisions draft is made, not at ingest: lines that start Action:, Action item:, TODO: or AI:, with their owner and due date as said (sb-ask(3), Action items). Nothing about them is added to the chunks, so the index stays derived from the source (LAW-13), and a chunk flagged instruction_like is never read for them (LAW-09).

What a model read (SB-6101, SB-6102)

A connector gives ingest the parts of a document it couldn't read as text (sb-connector(3), Scans, images and recordings): an image file (PNG, JPEG, WebP), each picture of a PDF with no text layer (in order, a page each), the pictures in a .docx or .pptx (with the slide that shows them), and an audio or video file (.mp3, .m4a, .wav, .mp4, .webm). The vision tier reads each picture, writing down its text in reading order and a one-line description of a diagram or chart (sb-cell(5), model.vision; the bundled prompt vision), and the transcribe tier turns each recording into timed lines, [HH:MM:SS] text (model.transcribe). At most 20 parts of a document are read. Each reader runs only while the evals job has gated it for the release (sb-evals(7), Readers; LAW-06) and in the model's region (LAW-33).

What a reader wrote joins the document after a marker, [Read by the vision model from NAME, page N] or [Read by the transcribe model from NAME], and is screened like any text: hidden text stripped, instruction-like text flagged, secrets dropped (Content is data, LAW-09). Every chunk that holds any of it carries read_by (vision or transcribe) and the marker's page: the AI mark of text a model read (LAW-28). Cites and search results carry it, the web UI shows Read by a model from a scan or picture or Transcribed by a model from a recording, and the chat apps say the same after the cite. It is never shown as the document's own words. A part no gated reader read (none configured, not gated, over the budget or the length cap, or a reader that failed) is skipped and counted on the connector's health (unread, sb-admin(3)) and in sb_ingest_parts_unread_total{connector, part}; the document's own text is indexed as before, and the part is read at the document's next version. A recording is a transcript and a picture an image to search's type= (sb-ask(3)).

Chunks

A document becomes chunks in a fixed order: normalise (line endings, trailing space), split into paragraphs, then pack paragraphs into chunks of at most 1,200 characters. A paragraph longer than that is cut at the last space before the limit. Boundaries depend only on the text, so the same text always gives the same chunks, and an edit to one paragraph changes only the chunks that contain it.

Each chunk also records its lines (SB-3006): the numbers of its first and last line in the document's own text, counted from 1, for links that open a source at the cited lines (sb-connector(3), code: github).

Each chunk's id is derived from tenant, cite and span, so ingesting the same (source, version) twice writes exactly the same chunks: ingest is idempotent. A newer version replaces all of the document's chunks in one write. An older or equal version than the one indexed changes nothing.

Embeddings come through the Embedder port. By default cells use a deterministic local embedder (feature hashing, 64 dimensions) that needs no network. A cell can instead embed with an OpenAI-compatible embeddings endpoint (embed in sb-cell(5); SB-1710), such as the model server on a self-hosted cell's own machine. Changing the embedder rebuilds the index from the sources: the ingest service records the embedder's id and dimensions under the cell's state, and when they differ at start it drops the index and starts every connector's sync again from the beginning, so no chunk is ever searched with vectors from two embedders; the Postgres index changes its vector column's size when it is empty (LAW-13). Chunks are written through the Index port; the in-memory index serves development and tests, and the Postgres/pgvector adapter comes with the retrieval work.

Pages and slides (SB-5205)

A connector may say where each page of a document starts in its text (Pages, in runes; sb-connector(3)). The folder connector does for a PDF, where each content stream is a page (one per page for the PDFs office tools write), and for a .pptx deck, where each slide is one. Each chunk keeps the page or slide it starts on (page, from 1), every cite of it carries it, and the passage view says it. A document without pages, and a chunk indexed before pages were kept, have page 0 and cite as before. Like every field of a chunk it depends only on the source, so a rebuild gives the same pages (LAW-13).

Sections (SB-3002)

Each chunk records its section: the text of the nearest heading line at or above the chunk's start, at most 120 characters, or nothing when there is none. A heading line is a Markdown heading of level 1 to 3 (#, ## or ### and a space). The folder connector writes the headings of the files it reads as such lines: Word paragraphs styled Heading 1 to 3 (and Title), OpenDocument headings (text:h), and HTML h1 to h3, and a meeting transcript's cue start times (### 00:12:40; SB-3701). A section is data: it is shown on the cite and never changes routing, ranking or any check (LAW-09). It is computed from the text, so a rebuild fills it in for every document (LAW-13).

Microsoft 365 labels (SB-5902)

A SharePoint or OneDrive item's Purview sensitivity label is its source label: sb-cell(5) labels.microsoft maps each label id to public, internal, confidential or restricted, and an id it doesn't map is restricted until an admin maps it (LAW-03: unknown never lowers a label; LAW-32). The label rides on every chunk as Drive's does, so answers and drafts carry the highest of what they cite. The health report lists the unmapped ids and their counts (unmapped_labels).

Spaces and labels (SB-1005)

In a cell with spaces (sb-spaces(7)), ingest routes every document version before it writes a chunk, so nothing is ever indexed without knowing which spaces hold it and how sensitive it is:

  1. Location. The connector reports where the document lives (sb-connector(3)): a Drive file's folder path and name (/Finance/Q3/Forecast), a Slack message's channel (#eng-platform), a Linear issue's team key (ENG), a HubSpot record's type (deals).
  2. Spaces. A space holds the document if one of its scope patterns for the document's connector kind matches the location. In a pattern, ** matches anything, * matches anything but /, and every other character matches itself, so /Finance/** holds everything under /Finance/, and #eng-* holds #eng-platform. A document can be held by several spaces, or by none.
  3. Label. The source's label wins where the source has one (a Drive classification label; a private Slack channel is confidential). Otherwise the label is the strictest default among the spaces that hold it, on the ladder public < internal < confidential < restricted, so a document in a restricted space and an internal one is restricted. A document no space holds, with no source label, is internal. A source label the cell doesn't know is restricted: unknown never widens.

Every chunk of the version carries its label, its holders (spc_NAME ids) and the routing fingerprint: a hash of every space's id, label, scope and field allow-lists, and a routing version that changes when what ingest records about a document changes (version 2 adds the source owner, so every document is routed again once after the upgrade; SB-1401). When a manifest apply changes a scope, a label or a field allow-list, the fingerprint changes, and the next sync re-routes every document whose chunks carry the old one, before it handles new changes. A document the source can't give while it is re-routed (deleted, moved, out of reach) is taken out of the index, counted in sb_ingest_reroute_dropped_total{connector}, and the sync goes on: it is never left routed by an old configuration, and one document never stops a connector's sync. It returns when it next changes at the source, or on a rebuild (SB-1401). Routing depends only on the document's location and label and the manifest, so a rebuild routes every document exactly as before (LAW-13). A cell without spaces routes nothing: chunks carry no label and no holders, as today.

Sensitivity in front matter (SB-5405)

A Markdown document's front matter sensitivity: (public, internal, confidential or restricted) is read at ingest and raises the label its source or space gave it, never lowers it; a value that isn't one of the four is restricted. Drive labels are read as before (sb-connector(3)). A note published from cites carries their highest label into its own front matter, so the label travels into the index again (LAW-32).

Rebuild

The index is derived data. It can be dropped and rebuilt from sources at any time, and the scheduled drill proves it (LAW-13). Each cell's ingest worker runs the drill weekly (ingest.Drill): it snapshots the (cite, chunk, ACL) set, drops the index, replays every source from the start of its change feed, and compares. The result and the rebuild time are recorded per tenant. Any difference is a LAW-13 violation and a Sev-1, reported with chunk ids and cites, never content.

First-seen times across a rebuild (SB-1708). A rebuild reads every version's seen before it drops the index and gives each version the same time again when it is replayed, so a rebuild doesn't make old documents look new. A version the rebuild meets that wasn't indexed before (one that changed while the index was being dropped), or every version when the old index can't be read (a lost index), gets the rebuild's time and is marked as rebuilt. "What changed" never lists a rebuilt version, and the weekly report doesn't count one, so a rebuild never shows as a week of changes.

LAW-09, LAW-13, LAW-01.
