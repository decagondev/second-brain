sb-ask(3)

NAME

sb-ask — POST /v1/ask, GET /v1/search, GET /v1/traces/{id}, POST /v1/feedback, /v1/saved, /v1/shares, /v1/questions, GET /v1/start, POST /v1/handover, GET /v1/handover/people, GET /v1/changes, POST /chat/mattermost, POST /chat/mattermost/actions, /v1/spaces/NAME/evals, POST /v1/access-requests

SYNOPSIS

POST /v1/ask
{ "question": "What's our refund approval limit?" }

DESCRIPTION

POST /v1/ask runs the ask agent for the signed-in user. The answer is built only from chunks that passed live authorisation for this user at this moment. Each claim either carries citations to doc@version or is marked uncited. How candidates are found and checked is in sb-permissions(7).

How the ask agent runs, exactly

  1. Validate. question must be 1 to 4,000 characters after trimming, and sources may name only docs, chat, tickets, crm, code, hris or accounting. Unknown fields are ignored (sb-api(3), Versioning). Anything else is EINVAL. Fair share (SB-2305): each person may ask asks_per_minute times in any minute (sb-tenant(5), default 6), counted by the cell in its memory over a sliding minute. One more is ERATE (HTTP 429, with Retry-After and retry_after, the whole seconds until the oldest of the minute's asks is a minute old), with no model call, and is stored as a trace of agent limited with no question, so the weekly report counts it. The chat apps reply with the same wait. Search, saved questions, sb tenant verify's sampled asks and everything else are not limited; a restart forgets the minute.
  2. Retrieve and check live as in sb-permissions(7). With sources, candidates of other kinds are dropped before the live check. In a cell with spaces, every candidate first passes the space, label and barrier checks (sb-permissions(7), Spaces, labels and barriers) with the asker's read context; only the chunks they allow go into the live ACL batch, and the ACL still decides each of those. An ask in a space uses only what that space holds. A company-wide ask uses the union of the asker's spaces, plus public and internal content from spaces they aren't in; confidential and restricted content comes only from spaces they're a member of (SB-1006).
  3. No allowed context: the model is not called. The answer is one uncited claim saying nothing the user can open answers this, with notice no_access if any candidate was refused, or no_sources if there were none.
  4. Compose: the bundled answer prompt (with language, one more line: "Write each claim's text in German. Keep every label exactly as given.", or English or French), the allowed chunks as data blocks and the question go through the model gateway (sb-agents(7), MODEL GATEWAY). The composer decides citations (sb-citations(7)). Each stripped label is logged as citation_spoof with the trace id and the label, never the claim text.
  5. Notice: most_uncited when more than half the claims are uncited; notice_stale and notice_sync as above, beside it.
  6. Trace: every answer gets a new trace id tr_…, returned in the body and in X-SB-Trace, and stored with the answer and its decision list for 30 days.

Conversations. A request without conversation starts one, and the response carries its cv_… id in conversation. A later turn sends only the user's earlier questions to the model, never earlier answers or chunks: everything cited is retrieved and checked live again, so an earlier turn can't carry content the user has since lost access to. A cv_… id that isn't this user's is EINVAL, the same as one that doesn't exist. Short conversations (SB-2901): a later turn sends at most the last 8 earlier questions, oldest first; any before them are left out of the prompt, and the response says how many in earlier_dropped. Nothing is removed from the stored conversation, and the trace keeps the turn's place in it. The web UI then says the earliest questions weren't used and offers Start fresh, which starts a new conversation. Branch a conversation (SB-5206): POST /v1/conversations/ID/branch { "at": N } makes a new conversation of the caller's own with the first N questions of conversation ID, and answers { "conversation": "cv_…", "from": "cv_…", "at": N }; the next ask with it goes on from question N in another direction, and ID is left as it was. Only questions are copied, never an answer. A conversation that isn't the caller's, or an N outside 1 to its length, is EINVAL. The web UI's Ask from here on an earlier answer does this and keeps the conversation it left in the browser, under Other branches, until sign-out; each branch downloads on its own.

@ and / in the ask box (SB-5207). In the web UI, a question ending @WORD offers the spaces the asker is in whose name starts with it (Ask in), the stewards and document owners of the space asked in whose address starts with it (Documents of, the person's documents on the Documents tab), and up to 5 documents a search for it finds (Ask about, which narrows the ask to that document, Documents above), each from the endpoint that checks as the asker: GET /v1/spaces, GET /v1/spaces/NAME/people and GET /v1/search. Picking one takes the @WORD out of the question. A question starting / offers the space's skills, below, and its starter questions (Starter questions, below). Nothing is offered that those endpoints wouldn't show the asker.

Skills (SB-4601). A question that starts /NAME (a slash, a skill's name and a space) loads the skill NAME of the space asked in, or of its department (sb-space(5), skills; sb-agents(7), Skills): /weekly-update What did we ship?. The /NAME is taken off before anything else, so the search, the live checks, the glossary and the conversation see the rest only, exactly as without the skill; the skill's instruction goes to the model after the agent's prompt, as one more line, and changes how the claims are written, never what they may cite. The response and its trace carry "skill": "NAME". An unknown name, a skill in a company-wide ask, or nothing after the name is EINVAL. A research question (Research reports, below) and a routine's saved question may start with /NAME too: each sub-question, and each run, is asked with the skill. GET /v1/spaces/NAME/skills lists a member's skills there, { "skills": [{ "name", "instruction", "from"? }] }, from the department a team inherits one from; the web UI offers them when the question starts with /.

Answers in the asker's language (SB-3003). language changes only the language the claims are written in. Retrieval, the live checks, the citations, the titles, sections and passages are the same as without it, and stay in the source's own language. An uncited claim is marked in every language (LAW-14). The language isn't stored with the question; the trace keeps the answer as written.

The cited passage (SB-3001). GET /v1/traces/{id}/passage?cite=CITE&start=N returns the text of one cite of that answer: { "cite": "docs:4f2a9c11@17", "text": "…", "cut": false }. Only the person who asked (or an auditor, as for the trace) may call it, only for a cite that is in the trace's answer (start picks the span when the answer cites a document more than once; without it, the first), and every call checks the person's access to that document again, now and as them (sb-permissions(7)), so an old trace or a share can't show text they have lost access to. text is the cited chunk's text at that version, at most 600 characters, cut after the last full sentence that fits (cut is then true). It is EPERM ("You can't open this source now.") when the live check denies or can't decide (LAW-01, LAW-03), and 200 with "gone": true and no text when the index no longer holds that version, which the UI shows as "This version is no longer indexed." A cite that isn't in the answer is EINVAL. Nothing is stored, and the text is never in a log (LAW-07). The web UI shows it as plain text in a block quote, never as markup (LAW-09).

Ask about a document (SB-3004). With documents, the candidates are only the chunks of those documents: those the search ranks, in its order, then the rest of each document's chunks in their order in it, so a document is found however the question is worded. They take every check as any candidate does, and the checks run first: the filter only ever narrows. A chosen document the asker can't open is refused like any other, so the answer is no_access; refused counts only the chosen documents. The three-chunk cap below doesn't apply, since every chunk is from a document the asker chose, but the usual budget does. Conversations, language and every notice work as without it.

One document, three chunks (SB-2902): of the chunks that pass every check and the one-copy rule (Copies, below), at most 3 of one document go into what the model reads for an answer or a draft, its best-ranked ones, in rank order; the rest of the budget goes to other documents. Search results (GET /v1/search) are unchanged.

Clarifying questions, exactly (SB-4901)

Before it searches, an ask looks for one ambiguity, in this order, and stops at the first:

  1. A term with two meanings: a glossary term the question uses (Glossary, exactly) that two spaces in scope define differently. The spaces in scope are the space asked in and, for a branch ask, its teams; for a company-wide ask, the department spaces of the asker's own (The right department). The choices are each meaning, TERM as SPACE uses it: MEANING, at most 4.
  2. Several departments: a company-wide question that uses glossary terms of two or more of those department spaces. The choices are About SPACE, at most 4, by name.
  3. No period: a question about an amount or a trend (how many, how much, total, revenue, spend, cost, sales, growth, trend, churn, headcount, hired, any case) that names no period (a year, a quarter, a month, a day, week, since, between, latest, now, all time and the like). The choices are This quarter, This month, This year and All time.

Every question ends with the choice just answer. With clarify: true the response carries the question and nothing else is done: no search, no model call, no trace. The asker asks again with the same question and choice; the choice goes to the model as one line after the question, The asker means: CHOICE, and the conversation keeps it with the question, so later questions read it (never memory, LAW-25); the search, the glossary and the table tool read the question as asked. just answer adds nothing. Only the first question of a conversation is looked at, so an ask is asked about at most once, and a choice that the question wouldn't be offered is EINVAL. Without clarify (the chat apps, MCP, routines, research steps, scheduled and triggered agents, rhythm steps) nothing is asked: the first choice is taken, given to the model the same way, and named in assumed, which the chat apps show first and an agent draft starts with. Eval cases, consultations and shadow runs are answered as asked. The choices come from the manifest's glossaries and fixed words, never from a document (LAW-09).

Glossary, exactly (SB-2203)

In a space with a glossary (sb-space(5)), step 2 first expands the question: each term the question uses, as a whole word, adds its meaning to the text that is searched and embedded, so "PO" also finds documents that say "purchase order". A term with a capital letter matches only as written ("IT", never "it"); a term in lower case matches in any case. Only the space's own glossary is used, and only in an ask or search in that space: a company-wide ask, or another space, never expands one (LAW-19). An entry that reads like an instruction (the patterns of sb-ingest(7), Content is data) is never used. The terms used go to the model inside one data block, <<data cite="glossary">>, never as instructions (LAW-09), and the response lists them, "terms": [{ "term": "PO", "means": "purchase order" }], which the web UI shows at the foot of the answer or results. The stewards' review list names the flagged entries, "glossary_flagged": ["TERM"…], so they can fix them.

Who to ask, exactly (SB-1702)

Every chunk carries its document's owner at the source (an email, SB-1203). The owner is looked up in the directory when the answer is built, and shown only if exactly one active user has that email; a deprovisioned, duplicated or unknown owner is left out, and a directory that can't answer leaves every owner out rather than failing the answer. Owners come only from the answer's cites, and a cite is only ever a chunk that passed the live check for this asker, so nobody learns who owns a document they can't open (LAW-01, LAW-12). Ownership at the source is the only signal: the cell builds no activity, chat or expertise profile of anyone. Caretakers (SB-3405): when a document's owner at the source is no active user, and a steward of the space named a caretaker for it, the caretaker is shown instead, with "caretaker": true on the owner, as long as they are one active user; a deprovisioned caretaker is shown as nobody (LAW-12). Whenever the source names an owner who is one active user, that owner is shown and the caretaker isn't.

Saved and shared questions, exactly (SB-1703)

A person can keep a question and pass it on. Only the question's text is kept, never an answer: opening a saved or shared question asks it again, live, under the access of whoever opens it.

Endpoint Does

Watching (SB-2104) runs the question as a search (no model) as its owner, in its space, and keeps only the SHA-256 of the result set: each result's cite, which carries the version, sorted. Each week, with the digest (Notifications, below), the search runs again as the owner, now, and a different hash tells them the sources changed. A source they can no longer open drops out of the set, so it counts as a change, but nothing names it; no answer and no result is kept (LAW-07). A watched question whose owner is no longer active is skipped.

The link /q/sh_… opens the web UI on the shared question with an Ask button; asking it is an ordinary POST /v1/ask by the recipient, so they see only what their own access allows, never the sharer's answer (LAW-01). Creating a share writes an access audit row whose subject is the share id and whose payload_sha256 is the SHA-256 of the question; the text itself never reaches a log or the audit log (LAW-07). Saved questions and shares are cell records kept under the tenant's retention (and a space's shorter one), held by legal holds like conversations, and erased with the person (POST /v1/admin/subjects/erase).

What agents did as me (SB-4305). GET /v1/me/agent-runs lists every run an agent made as the caller in the last 90 days, newest first: { "items": [{ "kind", "agent", "space", "at", "title", "read": [{ "cite", "title" }], "hidden": N, "drafted": "…", "link" }] }. Numbers from tables (SB-4307). A model asked to add up a sheet gets the arithmetic wrong, so the ask agent does it in code. When a question asks for a number (how many, how much, a total, sum, average, mean, count, minimum, maximum, highest, lowest, largest, smallest) and what the live check allowed holds a spreadsheet (an .xlsx, .ods or .csv document, sb-ingest(7), Spreadsheets), the agent makes one more model call with the bundled table prompt: the model sees the question and, as data, each such sheet's name and first row (its column names), never its other rows, and answers with at most one plan: { "doc", "sheet", "where": [{ "column", "equals" }], "op", "column" }, op one of count, sum, average, min and max, at most 3 filters. Anything else, or no plan, and the answer is composed as without the tool. The table tool then runs in code: it reads every stored chunk of that version of the document, checked as the asker as any chunk is (LAW-01), rebuilds the sheet, keeps the rows where each filter's column equals its value (ignoring case and spaces at either end), and computes op over the column (count counts the rows; the others read numbers, a cell that isn't one is skipped). It reads only, writes nothing and calls nothing. Its result goes to the composer first among the sources, as a passage of that document with the document's own cite: "Table tool result: sum of Amount where Customer is acme-logistics, over Invoices!C2:C41: 12840.5 (12 rows)". The range counts the rows the index holds (a row with no value isn't one), the first being the column names. The answer carries it as table. The composer check (LAW-14): a claim that cites a spreadsheet and states a number that is neither in the text of the passages it cites nor the tool's value is dropped, counted in dropped. When the document isn't whole in the index, or a column isn't found, the tool returns nothing and the answer is composed without it.

Requests to a department, exactly (SB-4104)

A space with requests (sb-space(5)) takes requests from its members. GET /v1/spaces/NAME/requests gives a member { "space", "categories": [...], "due_days" }, with no categories for a space that takes none. POST /v1/spaces/NAME/requests { "category", "text" } sends one: the category is one of the space's, ignoring case, and the text 1 to 4000 characters, as a question. It returns { "id", "to", "category", "due" }. The request is a question to the space's stewards (Questions to the stewards, above) with request: { "category", "due_days", "due" }: due is the end of the day due_days working days after it was sent, in the digest time zone. It needs no answer first, and it is audited like a question (asked, reason "request to stewards", the text hashed). Claims, replies, notes and notifications work as for any question. On the asker's GET /v1/questions and the steward queue it carries request, and the queue marks it overdue once due has passed. Past due it climbs: a request takes each step up the tree (Up the tree, above) after its due_days, not 10, and the queue it reaches is told "1 request went past its due date in a team" (or "in its space" for the company-wide answerers): counts only, never its text or category. The brain routes and records a request; it never does it. A non-member is EPERM; a space without requests, an unknown category or no stewards is EINVAL.

Ask each department and hand off, exactly (SB-4501, SB-4502)

Ask each department (consult: true on a branch ask) answers as the branch ask does, then consults. The candidates are the teams of the branch the asker is a member of (the branch scopes the auth middleware issued, sb-spaces(7), The tree). A team is a candidate when it runs a department agent the manifest enables (the first one its agents lists, sb-agents(7)), and it is chosen when the question uses its glossary (with its department's, SB-3902) or names the team or its template, the rule the right department uses (SB-4007). Chosen teams are ranked by how many terms matched, then by name; the first 6 are consulted and the rest are over_limit. Each consultation is exactly the ask the asker would get asking that agent directly in that team (?space=TEAM with agent), with the same question, language and length: retrieval and every check run once, as the asker, in that space only, and its model spend is metered to that space (SB-4105). It takes none of the asker's asks per minute, keeps no conversation of its own, and is kept in the asker's trace. A consulted agent never consults (consult inside a consultation is EINVAL), never calls a tool (the table tool doesn't run), and shows no pin or suggestion. A team whose agent or space is switched off is paused; one whose call the model budget refuses is budget. LAW-27: a consultation runs as the asker, one level deep, and adds nothing the asker couldn't get by asking that space directly.

Asking for access, exactly (SB-2205)

Where an answer or a search counts sources the asker can't open, POST /v1/access-requests { "trace": "tr_…" } asks their owners to share them. The trace must be the asker's own, from the last 7 days. Only sources the source itself refused (source_denied in the trace's decision list) are asked about: one refused by a space, label or barrier check isn't, since sharing it at the source wouldn't open it, and a request across a barrier would tell the other side what was asked (LAW-22). For each such document, at most 20, the cell finds its owner at the source as for who to ask (exactly one active directory user with the email, else nobody), and sends that owner one access notification (Notifications, below): the asker's email and the document's title, which the owner can open, and never the question or the answer (LAW-07). It sends one request per asker, document and week; asking again that week sends nothing more. The response is counts only: { "sent": 2, "already": 1, "no_owner": 1 }, never which documents or who, so the asker learns nothing they didn't know (LAW-01); someone already named in the answer's people is still named there. An owner who has turned access off gets nothing, and the asker isn't told. A cell with no chat bot and no email to send from is EUNAVAIL. The web UI shows Ask the owners for access under "N sources were not shown", and then the counts.

Why not this document? (SB-5506) POST /v1/traces/{id}/why-not { "document": TITLE | LINK | KIND:ID }, for whoever may read the trace, finds the document among the space's (every space company-wide) and says why the answer didn't use it, checked as the caller now: used (it is cited), not_indexed (with the source's last sync when it is behind), outside_scope (not in the space, its label keeps it out here, or the ask was about other documents), dropped, excluded, retired, held, suspect, or ranked_below, with rank (its best passage's place among the 50 candidates, 0 when none was among them), cut (how many passages an answer reads) and closest (that passage's cite). The ranking is replayed for the trace's question from the asker's own conversation. A document the caller can't open at its source answers exactly as one that doesn't exist: { "reason": "no_such_document", "text": "No document you can open by that name." }. Web: Why not this document? under each answer.

The retrieval view (SB-5507) GET /v1/spaces/NAME/review/retrieval?trace=ID, for the space's stewards and only for an answer asked there that was reported to them (SB-3606) or rated unhelpful (SB-3604; otherwise EINVAL): the trace's question searched again as the steward, each ranked passage with its keyword_rank, vector_rank, fused score and why (kept, budget, per_document, retired, held or suspect), { "trace", "rows": [...], "hidden" }. Passages the steward can't open are counted, never named, and the asker's memory and exclusions play no part, so they are never shown. Web: Show the retrieval on a reported answer in the queue.

Memory over MCP (SB-5505): with the memory family (sb-cell(5), mcp_groups) and memory on, the MCP endpoint offers one read-only resource, memory://me (resources/list, resources/read), the caller's own lines, and a memory_propose tool. A proposed line passes the same checks as one typed in, waits in the person's memory as proposed (at most 10) and inbox (kind memory), and is never sent with an ask until the person confirms it in the web app: POST /v1/me/memory/proposals/{id}/confirm, or DELETE /v1/me/memory/proposals/{id} to dismiss, both refused (EPERM) for an API token, which is what an MCP client uses. Another person's memory is never offered.

When the model is down (SB-5602)

With no gated model to write an answer, an ask still runs every check and returns the best passages the asker can open (passages), with notice: "model_unavailable" and no claim: the web shows "No answer written: the model is unavailable." above them, and nothing is labelled as an answer (LAW-14). An ask that waited more than 20 seconds for a provider that is rate-limiting gets the same passages with notice: "model_busy", "No answer written: the model is busy. Try again in a minute." (SB-5703, sb-runtime(7), When the provider is busy).

Answered before, checked now (SB-5603)

An ask whose normalised question (lower case, words only), space, source kinds, language, agent, length and verified match an answer kept in the last 7 days reuses it, with no model call, when the documents this ask's own retrieval allows, checked live as the asker after retirements, holds and exclusions, are exactly the ones that answer was composed from, in the same versions: nothing it read has changed and the asker can open all of it now (LAW-26). Its cites are dressed again for now (owners, links, review marks). It carries reused (the day it was written), and the web shows "Answered on DATE, checked now" with Ask fresh (fresh). Only a first question with every claim cited is kept for reuse, and an ask with memory lines, exclusions, kept or dropped documents, a file, a collection, chosen documents, a skill, a consult or a clarifying choice never reuses or is reused. Near matches with other wording are never reused.

Where you left off (SB-5805)

GET /v1/me/left-off is up to 3 of the caller's own open things from the last 14 days, overdue first, then newest: { "items": [INBOX ITEM] } with kind question (a question they asked that waits on a steward, SB-1704), research (a research plan waiting for their approval or a checkpoint, SB-4903), action (an action they confirmed and haven't done, whose transcript they can open now, SB-4203) or wait (an overdue wait they set in a space they are a member of now, SB-4504), each with its link. Everything is read from the stores those live in, as the caller now, so an item they can no longer open isn't shown, and nothing new is kept. A new conversation on the web starts with them, and Not now hides them for the day in that browser; the person's first direct message to the Slack bot each day starts with them too.

The notice to everyone (SB-3207)

While an admin's notice stands (sb-admin(3), PUT /v1/admin/notice), the web UI shows it at the top of every screen, read from GET /v1/notice on load and every five minutes, and the chat apps put it as the first line of every answer, Notice: …. It is shown as plain text, never as a link or markup, and it is gone once its end time passes.

Spaces

GET /v1/spaces lists the spaces the asker is a member of, now, as {"spaces": [{"name": "finance", "label": "restricted"}]}, sorted by name. Spaces the asker isn't in are never listed, and a cell without spaces returns an empty list. A registry that can't answer is EUNAVAIL.

The chat app (Slack)

Staff can also ask from Slack with /ask <question> (SB-308). It is the same ask agent with the same laws. Only the entry point differs: Slack calls POST /chat/slack/commands for the command and POST /chat/slack/interactions for the Share button.

  1. Verify. The cell checks Slack's request signature with the signing secret from vault://tenants/TENANT/connectors/chat and refuses any request older than 5 minutes. The team_id must be the tenant's workspace. Anything else gets HTTP 401 and no reply.
  2. Map the person. The bot looks up the Slack user's email (users.info) and finds the one active directory user with that email (SCIM-provisioned, sb-identity(7)). No match, more than one match, or an inactive user gets an ephemeral reply saying the account can't be matched, and no answer. The bot never falls back to a shared or service identity.
  3. Answer privately. Slack gets an immediate ephemeral "Looking that up…". The answer follows through Slack's response_url (only https://hooks.slack.com/), also ephemeral, so only the asker sees it. The stale and sync warnings (notice_stale, notice_sync; SB-2701, SB-2704) come first, in the web UI's words. Claims show as text with their citations as links (<url|cite>). Uncited claims start with Uncited:. The reply ends with who to ask (the answer's people, each with the documents of theirs it cites), the notice, the refused count and the trace id.
  4. Spaces. In a cell with spaces, the channel the command was typed in picks the space: a space's channels in the manifest (sb-space(5)) list the channels that ask in it. A mapped channel asks in that space, and someone who isn't a member gets an ephemeral reply saying so and no answer, never a company-wide one. An unmapped channel, or a direct message, asks company-wide.

  5. Share. A Share in channel button posts the question and the citation links only, never the claim text, so each reader opens the sources under their own access. Only the asker can share, and the trace is read again with the asker's own scope.

  6. Save to the brain (SB-3703). A message shortcut, Save to the brain (callback id save_to_brain, through POST /chat/slack/interactions), sends the thread the message is in to the stewards of the channel's space (or questions_to company-wide), as a saved thread in their queue: who saved it, a link to it, and at most 50 of its messages, each as EMAIL: text with the author mapped by users.info, 4,000 characters in all. The cell reads the thread with the bot's token (conversations.replies). Only someone mapped to one active directory user can save one, and in a space's channel only a member; each save is audited (access, state saved, the SHA-256 of the text). Nothing is published: a steward's reply and Publish as a note publish it, or Discard drops it. The person gets an ephemeral "Sent to the stewards of NAME."

  7. Follow up in the thread (SB-5801). A reply in the thread under one of the brain's messages (a shared answer, say) continues the replier's own conversation in that thread: one conversation per thread and person (cv_t…, made from the tenant, the person and the thread, so nobody else can reach it), with the conversation's last 8 earlier questions sent as before (SB-2901). Each reply is checked again as the person who wrote it: their Slack user mapped to one active directory user and the channel's space, exactly as /ask is. The answer goes to them alone, as an ephemeral reply in the thread (chat.postEphemeral); one labelled confidential or restricted goes to their direct messages instead, and the thread gets an ephemeral "This answer cites confidential documents, so I've sent it to you directly." (LAW-32). Someone else's reply in the same thread starts their own conversation. The cell takes the events through the chat connector's POST /connectors/slack/events, the one events URL a Slack app has: a message whose parent_user_id is the bot (auth.test) in a channel the bot is in (conversations.info). A bot's own message, a reply under anyone else's, and another workspace's event are ignored.

  8. Ask in a direct message (SB-5805). A direct message to the bot is a company-wide question, answered in that direct message. The person's first one of the day (UTC) starts with up to 3 lines of Where you left off (below), each with its link.
  9. React to save (SB-5806). The reaction sb-cell(5) chat.save_reaction names (default brain), added to a message in a channel the bot is in, sends the person who added it one direct message: "You reacted to a thread. Save it for the space's stewards, or ask the brain about it? Nothing is read until you choose." with Save for the stewards and Ask about this thread. Only the reaction event is read until they press one. Save for the stewards saves the thread as Save to the brain does (6, above); Ask about this thread asks "What does this thread discuss, and what do our sources say about it?" with the thread as a file read for that ask alone (SB-3802), its text data, never instructions (LAW-09). Both run as the person who pressed, in the channel's space. A reaction in a channel the bot isn't in, or in a direct message, reads nothing.

Errors are ephemeral replies with the error's message and trace id. Slack scopes for the bot: commands for /ask, which answers through response_url, channels:history and groups:history for Save to the brain, and chat:write, im:write and users:read.email for notifications (Notifications, above), which are direct messages that never carry an answer. Follow-ups, direct questions and the save reaction need the bot events message.channels, message.groups, message.im and reaction_added, and im:history, reactions:read and chat:write (SB-5801, SB-5805, SB-5806); a confidential follow-up's direct message carries the answer, to that person only.

The chat app (Mattermost)

Sites that run their own Mattermost can ask from it with a slash command (SB-2005), for example /brain <question>. The command is a Mattermost custom slash command whose request URL is the cell's POST /chat/mattermost, method POST; the cell takes it when sb-cell(5) sets mattermost.base and mattermost.team_id. It follows the Slack app's rules, from the same code:

  1. Verify. The command's token (the form's token, or Authorization: Token …) must equal command_token in vault://tenants/TENANT/mattermost, read at every request, and team_id must be the tenant's team. Anything else is HTTP 401 and no reply.
  2. Map the person. The cell reads the Mattermost user's email with the bot's token (bot_token in the same secret; GET /api/v4/users/ID), and finds the one active directory user with that email. A deleted Mattermost user, a bot, a hidden email, no match, more than one, or a deprovisioned user (LAW-12) gets an ephemeral reply that the account can't be matched, and no answer.
  3. Answer privately. Mattermost gets an immediate ephemeral "Looking that up…", and the answer follows through the command's response_url, which must be the server's own /hooks/commands/ URL, also ephemeral. It is Markdown: the question, the stale and sync warnings in the web UI's words (SB-2701, SB-2704), each claim with its citations as links ([`cite`](url)), uncited claims marked Uncited:, who to ask, the notice, the refused count and the trace id. Claim text is escaped, so it can't become a link, a mention or formatting.

  4. Spaces. A space's channels (sb-space(5)) list Mattermost channels by name as they do Slack's: a mapped channel asks in that space, and someone who isn't a member gets an ephemeral refusal, never a company-wide answer.

  5. Share (SB-2105). The answer carries a Share in channel button, a message attachment action whose integration URL is the cell's POST /chat/mattermost/actions (sb-cell(5) base_url). Its context holds the trace id, the asker's Mattermost user id, the command's response_url and an HMAC-SHA256 over the three keyed with command_token; Mattermost doesn't sign action requests, so the cell checks that HMAC with the token read at the press, and anything else is HTTP 401. Only the asker can share: the pressing user_id must be the one in the context, mapped again to the one active directory user, and the trace is read again with that scope. The channel then gets, through the response_url as in_channel, the citation links only, never the claim text, exactly the Slack rule, so each reader opens the sources under their own access. Anyone else pressing it gets "Only the person who asked can share this answer." response_url lasts 30 minutes, so a later press says the answer can't be shared any more.

  6. Save to the brain (SB-3703). /brain save LINK, with a message's permalink (or its post id) and typed in the same channel, sends that message's thread to the stewards of the channel's space, as Slack's message shortcut does (above): the same mapping, limits and audit. The cell reads the thread with the bot's token (GET /api/v4/posts/ID/thread) and refuses one from another channel than the command's, so nobody saves a thread they weren't in. /brain save alone explains how; any other text is a question.

  7. Follow up in the thread (SB-5801). An outgoing webhook on the channels the bot is in, whose callback URL is the cell's POST /chat/mattermost/events and whose token is events_token in vault://tenants/TENANT/mattermost, posts each new message. A reply whose thread's root is the bot's own post (GET /api/v4/posts/ID, GET /api/v4/users/me) continues the replier's conversation in that thread under the Slack rules (7, above): re-authorised as them, answered as an ephemeral post in the thread (POST /api/v4/posts/ephemeral), and a confidential or restricted answer to their direct messages instead (LAW-32). A wrong token or team is HTTP 401. Mattermost sends outgoing webhooks for channel messages only, so a reaction to save and direct questions are Slack's alone; /brain save LINK stays the way to save a thread here.

The bot account needs to read users' emails (the System Console's Show Email Address for it) and to create direct channels for notifications (Notifications, above); replies and shares go through response_url.
